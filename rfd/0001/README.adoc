= RFD 1 Unified event storage for interactive telemetry

== Summary

Lighthouse will provide Scuba-style recent-data exploration over logs, spans,
and structured application events through one logical event model. Native
metrics remain separate because series identity, temporality, counters, gauges,
histograms, stale markers, and Prometheus semantics require a different access
path.

The design preserves every accepted event at full resolution. Query-time
approximations, bounded accelerators, and partial-result policies may reduce
interactive cost, but none may silently discard accepted source events or make
an unaccelerated field unqueryable.

This proposal is still in discussion. The benchmark program establishes the
storage and latency envelope before the MVP workload contract is committed. See
link:IMPLEMENTATION.org[the implementation and validation checklist] and the
link:experiments/README.md[experiment record].

== Product contract

The target workflow is:

....
alert -> compare time ranges -> group by any retained field
      -> identify an outlier -> inspect exact representative events
....

Lighthouse adopts Scuba's flexible event exploration, mandatory time bounds,
storage-node partial aggregation, and fast drill-down. It does not adopt
Scuba's memory-authoritative serving, silent sampling, short-only retention, or
unlabelled incomplete answers. Kraken is supporting evidence for future scale
techniques, not the product model or an immediate reason to build a custom data
plane.

The MVP supports filtering, grouping, time series, rates, histograms, heatmaps,
percentiles, top-K, comparisons, and bounded raw-event retrieval. Joins and
arbitrary general-purpose database workloads are outside the interactive path.
Every query requires a tenant, dataset, and bounded time range.

Freshness, p50/p95 latency by query class, concurrency, retention, and cost
budgets remain open until controlled multi-day query measurements are complete.

== Event and instrumentation contract

Producers emit a versioned envelope containing tenant and dataset identity,
stable event and immutable batch identities, source and observed timestamps,
event kind, service and deployment context, trace correlation, structured
attributes, exact payload, and explicit upstream sampling metadata.

Instrumentation libraries must be asynchronous, batched, compressed, and
backpressure-aware. They expose accepted, rejected, retried, sampled, and
dropped counts. They must not silently sample. Upstream-sampled events carry a
probability or weight so aggregates can compensate and disclose that they did
so.

Ingestion validates field count, field-name growth, event and string sizes,
declared types, reserved fields, and sensitive-data policy before acknowledging
the durable batch. Additive fields are permitted; incompatible type changes are
recorded and rejected or isolated according to versioned tenant policy.

== Serving and durability architecture

The MVP has three logical planes:

* The ingestion plane authenticates, validates, redacts, applies quotas,
  durably accepts immutable compressed batches, and feeds idempotent consumers.
* The query plane stores recent normalized events in ClickHouse, computes local
  partial aggregates, and merges them behind a coordinator with deadlines,
  cancellation, scan/group/memory budgets, and workload isolation.
* The control plane owns datasets, schemas, retention, privacy classes, quotas,
  field observations, acceleration policy, and query audit records.

The durable log and immutable object archive are authoritative for replay;
ClickHouse is reconstructable serving state. A normalized hot event table owns
common routing, time, service, severity, trace, and typed measure columns plus
the benchmark-selected flexible long tail. An exact payload table or archive is
joined only for bounded drill-down, not ordinary aggregation.

== Physical event representation

Long-tail fields use ClickHouse `Map` for the MVP. Common schema-stable fields
become physical columns only when they are broadly useful across tenants or
required for routing and correctness. Per-tenant arbitrary columns are not
added to the shared table.

Tenant-specific acceleration is expressed through bounded secondary objects:
indexes for selective equality predicates, aggregate states or projections for
known dashboard shapes, metadata catalogs for field discovery, and normalized
query-result caching. Raw events remain the semantic fallback. Acceleration is
manual or dashboard-requested initially; workload observation may recommend it,
but automatic activation waits for proven per-tenant storage, cardinality,
backfill-CPU, and maintenance budgets.

The system does not array-join every attribute into an inverted index. The
initial proof of concept expanded 62.4 million events into 3.73 billion string
index rows while leaving broad metadata scans unsafe, demonstrating why derived
storage must be bounded and justified by measured workload benefit.

== Cardinality and multi-tenancy

Cardinality is a control-plane and query-admission concern, not a reason to
delete source values. The ingestion stream maintains bounded sketches for field
presence, type, approximate distinct count, top-K, value size, and growth rate.
It never materializes a complete high-cardinality value dictionary merely to
measure cardinality.

Budgets apply per tenant and dataset to event size, field count, field-name
growth, ingestion rate, retained bytes, derived bytes, scan bytes, result
groups, memory, and concurrent work. High-cardinality grouping can use bounded
top-K or approximate distinct algorithms in interactive mode; guarded exact
execution remains available when its estimated cost fits policy or as an
asynchronous job. Dashboards and exploratory scans use separate workload
classes so one tenant cannot consume the cluster.

== Query semantics and result truthfulness

Exact versus approximate math is independent from complete versus partial data
coverage. Every result reports the execution mode, selected storage path,
freshness watermark, expected and scanned shards or partitions, source sampling
adjustment, bytes and rows scanned, and whether the answer is partial.
Billing, compliance, security enforcement, and other complete-result workloads
must reject incomplete execution or use a separate policy.

Mergeable local aggregates include count, sum, min/max, sum-plus-count average,
compatible histograms, t-digest or DDSketch quantiles, HyperLogLog distinct
counts, and bounded heavy hitters. Coordinators receive aggregate states rather
than matching raw rows except for explicitly bounded event samples.

== Distribution and growth

Beyond one node, local `ReplicatedMergeTree` tables sit behind ClickHouse's
`Distributed` engine. Events use a stable hash of `(tenant_id, dataset,
event_id)`, allowing a large tenant to consume all shards. Tenant/dataset/time
queries initially fan out broadly and aggregate locally. Adding shards may let
old placement expire with retention rather than requiring immediate retained
data redistribution.

Lighthouse will not implement a Kraken-style virtual-partition placement layer
before measurements show that fixed per-shard latency, fanout traffic, dataset
placement requirements, or topology churn justify its versioned metadata and
recovery complexity. Stable identities preserve that future option.

== Measured evidence

The benchmark corpus is GCP Logging data originally represented as JSON and
compacted into Parquet. GCP-equivalent logical bytes use the available monthly
32 TB billing-scale estimate provisionally; the exact source metric and scope
remain to be verified.

* link:experiments/006-one-day-map-json-scale-load.md[Experiment 006] loaded a
  547,356,173-row natural day. `Map` completed while native JSON was stopped at
  63.2% after descriptor, part-count, and inode pressure. This selects `Map` for
  the current MVP, not for every possible workload.
* link:experiments/007-full-day-map-query-baseline.md[Experiment 007] established
  raw full-day latency and showed that repeated dynamic predicates can benefit
  materially from ClickHouse's query-condition cache, while broad scans still
  require workload-aware acceleration.
* link:experiments/008-tenant-attribute-acceleration.md[Experiment 008] showed
  schema-stable promoted fields and configured aggregate states can accelerate
  measured tenant workloads, but their storage and maintenance cost requires
  tenant budgets rather than global promotion of arbitrary fields.
* link:experiments/009-split-hot-events-payload.md[Experiment 009] preserved
  matching rows and checksums while splitting normalized hot events from exact
  payload. Exact lookup was about 12 ms on SSD and 351 ms on bulk storage in the
  measured fixture.
* link:experiments/010-ten-day-split-storage-load.md[Experiment 010] loaded and
  checksum-validated 5,689,254,359 rows across 240 hourly windows: 10.81 TB of
  logical input became 1,000.85 GiB of normalized hot data and 708.48 GiB of
  exact payload, 16.98% of logical input in total.
* link:experiments/011-ten-day-query-baseline.md[Experiment 011] completed 60
  controlled ten-day raw measurements. Schema-stable service/severity filtering
  was fastest at about 12 seconds. Dynamic `Map` predicates took 15.5 to 16.3
  minutes cold and 6.9 to 8.1 minutes warm; heatmap and percentile scans took
  12.1 to 16.8 minutes. Deterministic exact payload lookup took 919 ms on its
  first ClickHouse-cold access and 62 to 73 ms thereafter.
* link:experiments/012-ten-day-acceleration-validation.md[Experiment 012]
  rebuilt two configured attribute indexes and two dashboard aggregate paths
  over all ten days. Derived storage was 31.80 GiB, or 3.18% of normalized hot
  storage. Attribute indexes improved demanding exact full-match aggregates by
  49x to 263x but still took 3.7 to 9.3 seconds for highly prevalent values.
  Dashboard aggregate states answered rate, heatmap, and percentile fixtures in
  75 to 124 ms, improving raw execution by 448x to 13,315x. All 30 correctness
  anchor checks passed.

These results support the split `Map`-based serving baseline and demonstrate
that ten-day retained capacity fits the current host. They also reject broad raw
`Map` scans as an interactive path and require bounded indexes, metadata
catalogs, and mergeable aggregate states with raw fallback. They do not yet
prove sustained production ingestion, mixed concurrency, cluster fanout,
cold-tier aggregate routing, or the 100 TB architecture.

== Privacy and operations

Sensitive fields are classified and redacted before durable acceptance.
Policies include reserved-field ownership, token and secret detection,
field-level access controls, tenant isolation, encryption, audit logs, raw
export restrictions, retention, and deletion workflows. Arbitrary request
bodies, headers, SQL parameters, or credentials are not accepted by default.

The system publishes ingestion acceptance and lag, archive durability, schema
conflicts, field growth, storage and derived amplification, partition skew,
query queue and stage latency, scan cost, coverage, cancellation, and expensive
tenant telemetry to an independent operational path.

== Alternatives

Separate log and span tables were rejected as the user-facing storage boundary
because cross-event exploration and trace-correlated logs are core behavior.
Separate physical components remain permissible behind the unified contract
when measured access paths require them.

Putting native metrics into the event table was rejected because it combines
incompatible semantics without improving event exploration. Keeping only raw
JSON was rejected because common routing and filtering repeatedly pay extraction
cost. Indexing every field was rejected because its amplification is unbounded.
Ingestion sampling was rejected because it conflicts with full-resolution
accepted data.

== Open decisions

The proposal cannot move to `committed` until the implementation checklist's
MVP exit criteria are met. The key unresolved choices are explicit SLOs and
retention, durable acknowledgement and deduplication semantics, initial tenant
budgets, synchronous versus asynchronous exact-query limits, object-backed
ClickHouse versus explicit archive routing, and the shard count or workload at
which broad fanout merits virtual partitions.
