= Acceptance and replay implementation

Checklist ownership: link:acceptance-and-replay.adoc[Acceptance and replay].

== PoC-required: Collector compatibility and normal path

Depends on the product fixture and tenant policy. These tasks replace the custom
batch receipt and mandatory durable-log/archive implementation path.

* [ ] Pin Collector components/configuration and ClickHouse versions; send standard OTLP logs, traces, and metrics through the gateway and verify unified event mapping, separate native metrics, typed attributes, resource/scope data, timestamps, and trace correlation.
+
Experiment 018 pinned `otelcol-contrib` v0.161.0 with ClickHouse 26.8.2.7-lts and
measured the direct mapping (logs/traces/metrics sent, separate metric tables,
resource/scope/record separation for logs and metrics, timestamps, trace
correlation). It also measured the gap: the stock ClickHouse schema stores every
attribute as a string `Map`, drops span scope attributes (`otel_traces` has no
scope-attributes column), and keeps duplicate keys, so the typed unified-event
mapping is not satisfied. These are characterization measurements against the
pinned components, not checklist completion. See
link:experiments/018-collector-compatibility.adoc[Experiment 018].
+
Product tree: the owned exporter and the Collector distribution live in
https://github.com/toudai-dev/collector[toudai-dev/collector], which owns the
component pins; ClickHouse stays pinned to 26.8.2.7-lts by `flake.nix`. Still open:
there is no product gateway configuration yet, the owned exporter does not map native
metrics, and no standard-OTLP run of the product build is recorded as an experiment.

* [ ] Define application-event encoding and internal identity assignment without requiring proprietary producer batch IDs; verify what survives SDK retries and Collector rebatching.
+
Experiment 018 observed that exporter queue batching merges separate requests
into one downstream request while preserving each resource group's attributes
(the captured batch was same-workspace only; cross-workspace batching was not
exercised), and that a producer retry after a crash inserted the same records
again with no deduplication. Application-event encoding itself remains open.
+
Experiment 021 measured one real cross-workspace downstream batch from the owned
exporter: a single logged export carried both synthetic workspaces and the four
stored event identities of its records, so batching across workspaces is observed
on batch contents rather than inferred from two requests sharing a queue. The
stored write identity is content-derived and survives producer retries, crash
recovery, and ambiguous-insert retries, which makes it usable for fixture
correlation; it is not a deduplication key, because two legitimate events with
identical content share it with a retransmission of the same request (the
`retry-duplicate` twin control stored four rows under one identity). No
notification-driven or proprietary batch ID is involved. Cross-workspace query
isolation and the final application-event encoding remain open. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].
+
Product tree: the owned exporter's `event_id` is still the content-derived Experiment 021
identity. Decision 0001 D5 assigns `event_id` at the gateway before batching, which the
exporter does not implement yet.

* [ ] Test the stock ClickHouse exporter against the required schema, routing, and canonical payload preservation; document any gap before implementing a custom component.
+
Experiment 018 documents the schema and typed-value gaps, the routing path
(credential-header routing plus a `resource` processor before batching), and a
`MATERIALIZED` promoted-column path with `create_schema: false`. Canonical
payload preservation, dataset routing, and a Toudai-managed schema remain
open. See link:experiments/018-collector-compatibility.adoc[Experiment 018].
+
Experiment 019 ran the `create_schema: false` managed-schema probe and captured
the exporter's actual `INSERT` from `system.query_log`: it names a fixed column
list, so a managed payload column receives its DEFAULT or type default (silently
empty, not rejected) and a `MATERIALIZED` projection can only promote a value a
mapping component already placed inside a known Map column. The `json: true`
mode was measured as a bounded control and does not preserve the typed contract
(non-finite doubles drop the whole request, integral int/double collide, bytes
lose their type, span scope attributes remain absent); Experiment 006's native
JSON scale rejection is unchanged. Canonical payload preservation therefore
needs a mapping component outside the stock schema; whether another stock
processor configuration can supply the type information was not ruled out
(conditional `where` statements and other processors were not tested), and
dataset routing remains open. See
link:experiments/019-typed-canonical-storage.adoc[Experiment 019].
+
Experiment 021 answered the component-boundary half of this item for the
provisional hybrid layout: the pinned exporter's INSERT lists are fixed in
`internal/sqltemplates/logs_insert.sql` and `traces_insert.sql` (logs store
`LogAttributes`/`ScopeAttributes` as string Maps with no typed column, spans have
no scope-attributes column), and a stock `transform` *can* create typed int and
double attributes and guard per key, so the blocker is the write path rather than
an absence of typed transformation. The experiment therefore built the smallest
bounded owned exporter (built into a small distribution with `otelcol.NewCommand`,
reusing `exporterhelper` for queue/retry/timeout) and wrote the canonical payload
plus the hybrid serving tables through a real OTLP path; typed attributes,
resource/scope namespaces, span scope, and lossless canonical retrieval were
verified against independent fixture expectations for logs and spans, with native
metrics outside the slice. Span timestamps were verified under the accepted
preserve-and-flag policy: a span with an unset start or end (OTLP encodes an unset
timestamp as 0, with missing timing taking precedence over the reversed
classification) or with its end before its start keeps its supplied timestamps and
an unavailable duration with an explicit diagnostic, alongside missing and valid
zero durations.
Long-term component boundary, dataset routing, and retained-scale qualification
remain open. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].
+
Product tree: the Decision 0001 DDL is in `clickhouse/schema` (`tenant_id`, `timestamp`,
`routing_epoch`, and a payload table on the S3-backed `toudai_payload` storage
policy); the owned exporter that writes it lives in
https://github.com/toudai-dev/collector[toudai-dev/collector]. Scratch runs of that
exporter against ClickHouse 26.8.2.7 with an S3 emulator inserted typed log and span
rows, stamped the epoch, moved an old payload partition to the S3 disk by TTL, and
retrieved it by `(tenant_id, dataset, event_id)`. Those runs are not recorded as an
experiment, and dataset routing still comes from a static `resource` processor, so the
item stays open.

* [ ] Integrate authenticated tenant policy before both exports; demonstrate normal-path ingestion and exact-event retrieval against independent fixture expectations.
+
Experiment 021 ran the provisional layout with real credential validation inside
the tested distribution (`bearertokenauth`: a request with no token or a wrong
token received HTTP 401 and produced no rows), a synthetic credential-to-workspace
binding stated as static, and independent fixture expectations for every stored
row. Forged resource/scope/record attributes could not override the trusted
workspace or dataset or inject the trusted-scope marker on the gateway path, and
the canonical payload was retrieved losslessly for the fixture. Dynamic key
resolution, rotation/revocation, dataset routing rejection, and broader
authorization guarantees remain out of scope and open. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].

== PoC-required: independent health telemetry

* [ ] Publish queue depth, export failures, rejected/dropped records, overflow backlog, and catch-up progress independently of ClickHouse; verify visibility during outages and disclose incomplete recovery coverage.
+
Experiment 018 verified the stock counters during outages
(`otelcol_exporter_send_failed_log_records`,
`otelcol_exporter_enqueue_failed_log_records`, `otelcol_exporter_queue_size`,
`otelcol_receiver_refused_log_records`, and the failover/`awss3` queue labels).
No overflow-object backlog or catch-up progress metric appeared in this
topology's scrapes (a statement about the tested configuration, not proof that no
stock component can expose one); such signals must come from outside the tested
pipeline. See
link:experiments/018-collector-compatibility.adoc[Experiment 018].
+
Experiment 021 added per-destination instrumentation in the owned component
(records and insert failures per destination, partial-write batches, rejected
records by namespace and reason, rejected batches, and cross-workspace batch
counts) and verified it during the outage, full-queue, permanent-failure, and
split-write phases; the outage phase also recorded that the destination endpoint
was actually refusing connections while the counters were scraped. The
rejected-batch counter cannot conceal a partial drop from the mixed-validation
phase: `all_records_rejected` increments only when no record survives validation,
a request whose rejection invalidates it (missing trusted scope) is counted under
that reason instead, and the component's batch summary reports the written and
rejected records of the same export. The remaining gap is explicit: a whole-batch
invalidation counts its reason but not the number of otherwise-valid records
dropped with it, and the stock helper's `sent` counter credits records as
received rather than rows written, so the component counters are the write-side
authority. Overflow backlog and catch-up progress signals remain
unimplemented in this slice. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].

== PoC-required: reconstruction and recovery decision

* [ ] Rebuild an isolated serving layout from retained canonical fixture data; compare identities, canonical payload checksums, and raw/derived results, leaving the original layout intact on validation failure.
+
Experiment 021 demonstrated only the bounded half of this: after a canonical-first
split write left canonical rows without serving rows, a recorded repair statement
derived a *minimal* serving row (routing identity, timestamps, kind, payload
checksum) from the retained canonical payload and landed exactly one such row per
canonical row (1/1 for the single failure and 7/7 for the retried failure). The
full typed serving representation was not rebuilt from canonical data by a
service, so this item remains open; the semantics phase verifies the
reconstruction rules against the fixture instead. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].

== Qualification: failure, overflow, duplicates, and recovery

These items are required before a production readiness claim and before RFD 0001 moves to `committed`. They do not block the PoC vertical slice defined in link:README.adoc#_poc_completion_gate[the PoC completion gate]; a PoC pass does not mark any of them complete.

=== Failure, overflow, and duplicates

* [ ] Configure direct ClickHouse export and object-store failover with separate catch-up collectors; verify fresh ingestion resumes without waiting for the overflow backlog and bound catch-up resource use.
+
Experiment 018 configured the `failover` connector with a stock ClickHouse
primary and an `awss3` overflow exporter: fresh ingestion resumed after ClickHouse
recovered while the spilled objects remained, and manual replay of a spilled
object through an OTLP receiver (not notification-driven catch-up) preserved the
trusted workspace. Catch-up resource bounds, a separate catch-up Collector
deployment, and SQS notification delivery remain open. See
link:experiments/018-collector-compatibility.adoc[Experiment 018].

* [ ] Map acknowledgement boundaries for receiver, processors, queues, connector, and exporters; inject crashes before/after enqueue and storage confirmation, including node loss, and record acknowledged-but-lost data and the supported failure envelope.
+
Experiment 018 measured producer-visible success as queue admission at the first
enabled queue: exporter helper queue (~3 ms to OTLP success, row visible at
14 ms), the failover connector queue (default enabled; 3.3 ms while the primary
retried and spilled), and the destination write when all queues were disabled
(1246 ms during an outage). A SIGKILL after admission lost the in-memory queue;
a `file_storage` queue recovered and drained the same batches after restart.
Node loss was not tested.
+
Experiment 021 re-measured the boundary on the two-destination hybrid write:
queue disabled meant the row was visible at acknowledgement (138.62 ms on the
committed run) while queue enabled acknowledged in 6.39 ms with the row visible
only at 0.36 s, and a
SIGKILL with a file-backed queue left `exporter_lighthouse__logs`/`__traces` on
disk and drained both destinations exactly once after restart with unchanged
identity. Because the component validates and canonicalizes the whole export
request before its first insert, a valid record followed by an invalid one in
the same request cannot half-write: the valid record was written to both
destinations, the invalid record is absent from both destinations, and `pushLogs`
returns success (the batch summary reported `records: 1, rejected: 1`). The policy
is per-record exclusion after queue admission, not whole-batch rejection and not
OTLP partial success: only a request with nothing surviving validation, or one
missing its gateway-injected trusted scope, is rejected as a whole (permanent,
non-retryable), and the producer still sees 200 either way. A queue-disabled
variant of that phase was not run. Node loss and multi-consumer queues remain
open. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].

* [ ] Exercise OTLP partial success, permanent/retryable errors, full queues, retry expiry, and simultaneous destination failure; verify rejection/drop counters and producer-visible behavior rather than assuming all-or-nothing acceptance.
+
Experiment 018 measured a permanent schema error (producer 200, seven retries,
then drop with `otelcol_exporter_send_failed_log_records`), a full bounded queue
(2 x 200 then 6 x HTTP 503 with `enqueue_failed` and `receiver_refused` counters),
and retry expiry. No OTLP partial success was produced: the stock receiver does
not validate records individually. Simultaneous ClickHouse and object-store
failure remains open.
+
Experiment 021 repeated the permanent-error, full-queue, and retry-expiry cases
on the hybrid write: a permanently broken canonical destination left both
destinations empty after five recorded attempts on the committed run, logged the
component error, dropped the
batch after the retry budget, and still returned 200 to the producer with no
per-record rejection; a bounded queue with a stalled destination returned
`200, 200, 503, 503, 503, 503`, and the requests admitted to the stalled queue
were not written when the process stopped. Simultaneous destination failure and
OTLP partial success remain untested. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].

* [ ] Inject an ambiguous successful ClickHouse insert, repeated object notifications, and Collector restart/rebatching; quantify duplicates and verify raw and derived results against fixture expectations before choosing deduplication mechanisms.
+
Experiment 018 quantified restart/re-batching and repeated replay duplicates
(replaying one spilled object twice produced two additional copies; final raw
counts 4/3/1/1 per fixture body) and confirmed that nothing deduplicates them.
An ambiguous successful insert (ClickHouse commits but the response is lost) and
real repeated S3 notifications were not injected.
+
Experiment 021 injected the ambiguous successful insert on the hybrid write from
both directions. With the *canonical* response lost, the destination committed
the canonical row while the response was withheld, the client failed at its 5 s
timeout, the exporter retried, and the result was two canonical rows with the
same identity and payload hash plus exactly one serving row, with `query_log`
showing two finished canonical inserts; that 2/1 shape is specific to this
injection direction. With the *serving* response lost, the retry re-attempted
both inserts and produced two canonical rows and two serving rows sharing one
identity and one payload hash (`query_log` shows two finished serving inserts),
so the serving destination does duplicate on retry as well. A producer retry of
an identical request produced two serving rows and two canonical rows with one
stored identity, and the twin control (a two-record request carrying two
legitimate events with byte-identical wire content, sent twice) stored four rows
under a single content-derived identity: that identity correlates fixture rows but
cannot separate identical legitimate events from a retransmission and is not a
deduplication key. Deduplication is unselected, so these duplicates are measured
rather than suppressed; repeated object notifications and derived results remain
open. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].
* [ ] Stop ClickHouse, verify overflow object contents, restore it, and drain catch-up; test failed inserts and missing/expired notifications, then verify recovery and object-cleanup safety.
+
Experiment 018 stopped ClickHouse, verified the spilled object's contents (trusted
workspace attribute plus the two records), restarted it, and replayed the object
through a catch-up receiver. Missing/expired notifications, object cleanup, and
drain safety remain open.
+
Experiment 021 stopped ClickHouse behind a shared-queue hybrid write: the
producer still received 200, an insert failure was counted, and after restart the
queued request landed exactly once in both destinations with a shared identity
and no duplicates. No object-store overflow was involved in this run, so the
object-content, notification, and cleanup parts of this item remain open. See
link:experiments/021-hybrid-layout-collector-integration.adoc[Experiment 021].
