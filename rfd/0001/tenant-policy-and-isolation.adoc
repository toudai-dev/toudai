= Tenant policy and isolation

This section defines tenant governance, metadata, privacy, and isolation.

== Accounts, workspaces, and keys

The resource hierarchy is `account -> workspace -> dataset`. An account owns
multiple workspaces; each workspace belongs to one account and contains its own
datasets, ingestion keys, policy, and telemetry. Workspace is the telemetry
isolation boundary. Names may repeat across workspaces; use stable workspace IDs,
not display names, for authorization and storage scope.

An ingestion key belongs to exactly one workspace. Multiple keys may target the
same workspace for independent rotation and revocation. The authenticated key
resolves the workspace and its owning account; producer attributes or dataset
selectors cannot override that binding. Ingestion keys grant write access within
that workspace, not read access or account/workspace administration.

Dataset routing is separate from authentication and stays within the resolved
workspace. A workspace may contain data from multiple services; `service.name`
does not implicitly create a workspace or necessarily define a dataset. The PoC
uses explicitly provisioned datasets and a configured default or explicit dataset
selector. Unknown datasets are rejected; automatic dataset creation is a later,
explicit permission decision rather than an ingestion side effect.

Use standard OTLP exporter headers for credentials, in SDKs or customer-managed
Collectors. The public header name and credential format remain implementation
choices. On a shared server-side Collector, authenticate each request and attach
trusted workspace scope before batching can discard request context. Never store
the raw API key in event attributes, overflow objects, or diagnostic logs.
Conflicting producer-supplied reserved scope fields must not change ownership.

Normal export, overflow, and catch-up preserve the original trusted workspace
scope. A catch-up service credential authorizes replay; it does not supply a new
owner for the records. Workspace deletion and key revocation need distinct
policies for already admitted backlog versus new requests; specify those policies
before enabling recovery rather than reusing a revoked producer key to replay.

Queries and administrative operations use separately authorized principals.
Authorize the requested workspace and dataset before planning, including metadata,
trace lookup, payload retrieval, exports, and future caches/jobs. Account ownership
of sibling workspaces does not make a workspace ingestion key valid in a sibling.
User roles and account-wide administration remain separate control-plane design
work; they do not weaken workspace scoping on telemetry APIs.

Existing design prose uses "tenant" as shorthand for this workspace isolation
scope. Historical benchmark `tenant_id` columns are not evidence of account-level
authorization: implementation must map that scope to a globally unique workspace
ID (or explicitly migrate the column). Do not reuse an account ID as `tenant_id`.
The corpus's ordinary `workspace_id` attribute is source telemetry, not a trusted
Lighthouse workspace identifier. Benchmark schemas and results stay unchanged.

== Cardinality and multi-tenancy

Cardinality is a control-plane and query-admission concern, not a reason to
delete source values. The ingestion stream maintains bounded sketches for field
presence, type, approximate distinct count, top-K, value size, and growth rate.
It never materializes a complete high-cardinality value dictionary merely to
measure cardinality.

Budgets apply per tenant and dataset to event size, field count, field-name
growth, ingestion rate, retained bytes, derived bytes, scan bytes, result
groups, memory, and concurrent work. High-cardinality grouping can use bounded
top-K or approximate distinct algorithms in interactive mode; guarded exact
execution remains available when its estimated cost fits policy or as an
asynchronous job. Dashboards and exploratory scans use separate workload
classes so one tenant cannot consume the cluster.

== Privacy and operations

Sensitive fields are classified and redacted before durable acceptance.
Policies include reserved-field ownership, token and secret detection,
field-level access controls, tenant isolation, encryption, audit logs, raw
export restrictions, retention, and deletion workflows. Arbitrary request
bodies, headers, SQL parameters, or credentials are not accepted by default.

The system publishes ingestion acceptance and lag, archive durability, schema
conflicts, field growth, storage and derived amplification, partition skew,
query queue and stage latency, scan cost, coverage, cancellation, and expensive
tenant telemetry to an independent operational path.

== Metadata catalogs

Maintain a small versioned registry for datasets, field definitions, privacy
classification, retention, quotas, and accelerations. A stream consumer, not
the ingestion gateway, maintains bounded time-aware observations for:

* known field names and observed types;
* field presence and last-seen time;
* approximate distinct counts using mergeable sketches;
* bounded top-K values and value-size distributions;
* type conflicts and cardinality growth rates; and
* promoted, indexed, and aggregated fields with coverage watermarks.

High-cardinality values such as event, trace, span, request, account, or run IDs
must not be enumerated for broad autocomplete. Their events are still retained
and exact filtering remains possible; cardinality governance limits metadata,
group result size, and acceleration cost rather than deleting accepted data.

Per-tenant and per-dataset policies bound event bytes, field count, field-name
growth, string length, indexed fields, derived bytes, groups returned, scan
bytes, query memory, and concurrent work. A cardinality spike creates a visible
policy event and may stop new acceleration or expensive grouping, but must not
silently sample already accepted events.

== Privacy and operational instrumentation

Field classification, secret/token detection, PII redaction or hashing,
tenant isolation, field-level access, query audit logs, and deletion workflows
must be designed before broad producer adoption. Arbitrary headers, request
bodies, SQL parameters, and authentication material are rejected or redacted by
default rather than relying on short retention after collection.

Lighthouse must expose telemetry outside its own serving path for at least:

* events received, accepted, rejected, dropped, and upstream-sampled;
* bytes and field counts by tenant and dataset;
* producer-to-durable, durable-to-archive, and durable-to-query lag;
* malformed events, type conflicts, policy versions, and replay backlog;
* cardinality, field-name growth, value sizes, and top-K churn;
* hot and archive bytes, parts, merges, retention, and acceleration coverage;
* query queue and execution latency, scans, groups, memory, cancellation, and
  timeouts; and
* response freshness, shard coverage, accuracy mode, and partial-result rate.

The telemetry system will become production-critical, so its minimum health,
durability, and alerting signals cannot depend exclusively on Lighthouse.
