= Acceptance and replay

== Collector-first PoC

OpenTelemetry compatibility is a requirement, not a later adapter. Standard OTel
SDKs and agents send OTLP to Collector gateways. Reuse Collector receivers,
processors, batching, exporters, retries, and connectors before implementing
custom ingestion components. Kafka and an archive-before-acknowledgement service
are not baseline dependencies.

The candidate path is direct ClickHouse ingestion with object-storage overflow
on downstream failure or sustained backpressure, followed by separate catch-up
collectors. This follows the architecture described in
https://clickhouse.com/blog/reliable-opentelemetry-ingestion-at-scale[ClickHouse's reliable OpenTelemetry ingestion report].
That report is operational evidence for a candidate, not proof of our schema,
tenant isolation, acknowledgement semantics, or loss/duplicate guarantees.

....
OTel SDKs / agents -> Collector gateways -> ClickHouse
                            |
                            +-- failure -> object storage
                                               |
                                        object notifications
                                               |
                                        catch-up collectors
                                               |
                                           ClickHouse
....

The notification queue carries object references, not all telemetry. Live and
catch-up deployments scale independently, but share downstream capacity; measure
and bound catch-up load so it does not starve fresh ingestion or queries.

== Reuse and Lighthouse ownership

Collectors own transport and pipeline plumbing. Lighthouse owns authenticated
tenant/dataset policy, unified log/span/event mapping, retained canonical content,
and query semantics. First test whether existing Collector processors and the
ClickHouse exporter can express the required mapping and routing. Add a custom
processor/exporter or narrow service only for a demonstrated gap; do not assume
the stock exporter implements Lighthouse's unified-event schema.

Pin the Collector distribution, component versions, configuration, and ClickHouse
version in the experiment. Establish support for OTLP logs, traces, and metrics;
logs/spans map into unified events while native metrics retain a separate model.
Define the application-event encoding using standard OTLP rather than requiring
a proprietary producer protocol. Compatibility testing must include resource and
scope attributes, typed values, timestamps, and trace correlation.

Authentication resolves an ingestion key to one workspace under an account.
Workspace-scoped validation/redaction precedes both ClickHouse and overflow
export. Preserve trusted workspace identity through batching and catch-up without
trusting producer-supplied account/workspace attributes. Policy integration is owned by
link:tenant-policy-and-isolation.adoc[tenant policy and isolation].

== Acknowledgements and retry semantics to establish

Do not equate an OTLP success response with a durable database or object-store
write. A response may follow admission to an asynchronous Collector queue.
For each pipeline stage, document when success is returned, where the data then
resides, and what survives process restart, node loss, queue exhaustion, and
simultaneous ClickHouse/object-store unavailability. Distinguish receiver receipt,
queued data, confirmed storage, and query visibility in operational reporting.

The previous custom immutable-batch receipt contract is superseded for the PoC.
Ordinary OTLP producers need not supply Lighthouse batch IDs or preserve a batch
across Collector rebatching. The PoC write identity is decided in
link:decisions/0001-poc-physical-layout.adoc[Decision 0001]: the gateway assigns
`event_id` at trusted-scope injection, before batching, and delivery is at least
once. An exporter retry after an ambiguous insert may store one identity twice
and a producer retry stores the same content under a second identity; the PoC
tolerates and discloses both and does not deduplicate. Stable IDs by themselves
do not establish deduplication, and Experiment 021 showed a content-derived
identity cannot separate identical legitimate events from a retransmission, so
the deduplication design waits for a measured duplicate rate in qualification.

Test standard OTLP partial-success and retryable/permanent-error behavior rather
than imposing all-or-nothing request acceptance. Document rejected record counts,
retry/drop policies, queue capacity, persistence, and maximum retry duration.
No lifetime exactly-once or bounded batch-idempotency guarantee is assumed.
Ambiguous insert outcomes and repeated object notifications can produce duplicate
delivery; determine and test their effect on raw events and aggregate states.
Do not claim exact original-event counts until that behavior is resolved.

ClickHouse's reference disables the primary exporter's sending queue so errors
reach the failover connector, while retaining synchronous retries and setting
`async_insert=1`, `wait_for_async_insert=1`. Queues elsewhere in the pipeline can
still acknowledge before durable export. Use these as a starting configuration,
not as proof of end-to-end durability. Persistent local queues may improve restart
survival but do not automatically survive node loss or guarantee timely catch-up.

== Overflow and catch-up

Overflow stores processed telemetry during downstream failure; it is not an
independent archive of every successfully ingested event. Test object publication,
notification delivery, duplicate notifications, failed inserts, and acknowledgement
of notifications only after the configured synchronous downstream outcome.
Specify cleanup/retention only after successful recovery, with a recovery procedure
for objects whose notifications are missing or no longer available.

While catch-up is pending, fresh events may be queryable before older ones.
Backlog size does not prove completeness of a particular tenant/time interval.
Expose recovery state and avoid asserting complete coverage from a maximum event
timestamp or from all shards responding.

== Retention, reconstruction, and the unresolved archive decision

On the normal path, durability depends on ClickHouse storage, replication, and
the chosen backup/restore policy. Preserve full-resolution accepted canonical
content within declared retention so derived layouts can be rebuilt when that
source remains available. The payload split measured in Experiment 009 is useful
layout evidence, not proof of backup or disaster recovery.

The PoC must demonstrate reconstruction from retained canonical data and a small
backup/restore test with an explicit recovery point. Overflow replay is a separate
test: it cannot reconstruct normal-path events that were never spilled. Validate
rebuilds in isolated tables before replacing a working serving layout.

Catch-up, reconstruction, and backup restore must apply the current
link:tenant-policy-and-isolation.adoc#_canonical_content_retention_and_deletion[deletion and retention rules]
before exposing results. Successful replay is not permission to resurrect expired
records or a deleted workspace, and policy-approved canonical content must not
be confused with unredacted producer input.

Whether every event also needs an independent canonical archive remains open.
Compare ClickHouse canonical retention plus backups against all-event archival
using required recovery point/time, transformation recovery, cost, and failure
domains. If an asynchronous all-event archive is selected, define a retention-safe
handoff before claiming independent replayability. If it is not selected, state
the limits of recovery after losing ClickHouse and its backups explicitly.

PoC acceptance requires an honest measured failure envelope, not an unsupported
zero-loss claim. Any observed loss, duplication, or incompatible mapping must
be recorded and resolved or explicitly accepted as a limitation before advancing
to production qualification.
