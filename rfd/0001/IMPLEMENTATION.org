* Context

Lighthouse is being designed as a ClickHouse-backed, Scuba-style telemetry
system for recent-data exploration. The initial proof of concept lives at
=~/workspace/inngest/lighthouse= and provides useful ingestion, query-planning,
Prometheus compatibility, schema, and staging performance evidence. This
repository is not required to preserve the proof of concept's physical schema.

The product workload, rather than Scuba's exact implementation, is the north
star: an engineer should be able to move from an alert to a time comparison,
group by any useful field, identify an outlier, and inspect representative exact
events without first predicting that query at ingestion time. The MVP contract
is intentionally not final until freshness, query-latency, concurrency, and
retention targets are agreed and the current multi-day benchmark is complete.

The product should provide a high-level event model rather than force users to
choose between logs and traces:

- logs, trace spans, and application-wide events share one event medium;
- a trace is a rendering of correlated events with span relationships;
- raw events remain available at full resolution without ingestion sampling;
- users can filter, group, aggregate, build heatmaps, and calculate percentiles
  over any retained event field;
- common dashboards remain fast through derived storage without limiting raw
  exploration;
- native metrics use separate time-series storage because their data model and
  access patterns differ from events.

The available performance corpus is under =~/storage/lighthouse=. It originated
as JSON log entries retrieved from GCP Logging and was compacted into Parquet.

* Goals

- Store logs, spans, and arbitrary structured events through one logical event
  medium with a common envelope. The query-serving columns and exact payload
  may use separate physical tables or tiers.
- Retain every accepted event and its queryable context at full resolution.
- Support exact raw queries and approximate or exact aggregate execution.
- Make interactive, arbitrary exploration possible without predeclaring every
  future query dimension.
- Accelerate known dashboard and incident workflows with bounded attribute
  indexes, materialized aggregate states, metadata catalogs, caching, and query
  routing while preserving raw fallback.
- Preserve field-type information in the logical contract and canonical event;
  use the benchmark-selected =Map= serving representation plus typed promoted
  columns or aggregate inputs only when measurement justifies them.
- Validate behavior at 1 TB, 10 TB, and 100 TB of GCP-equivalent uncompressed
  event data before considering a 1 PB clustered test.
- Measure storage amplification across the complete schema, not only base-table
  compression.

* Non-goals

- LogSQL or LogQL compatibility is not required in the initial design.
- A 1 PB benchmark is deferred until the 100 TB architecture is understood.
- Native metrics do not need to share the physical event table.
- Every arbitrary query is not required to have dashboard-class latency.
- Rollups do not replace or expire the full-resolution source events.
- Fully automatic physical-schema mutation is not an MVP requirement.
  Dashboards may request accelerations explicitly, and workload observation may
  recommend them; automatic activation requires per-tenant storage, field,
  cardinality, and backfill-CPU budgets.

* Settled Design Principles

** Unified events

One logical =events= medium stores logs, spans, and application events. Its
normalized query-serving table and exact canonical payload may be physically
separate. An =event_kind= discriminator affects ingestion validation and
rendering, not the event's queryability. Common queries can aggregate all event
kinds together.

Trace-specific fields such as trace ID, span ID, parent span ID, span kind, and
duration are nullable or have empty defaults for non-span events. Logs carrying
trace context are returned with spans when querying a trace.

** Separate native metrics

Native Prometheus or OpenTelemetry metrics remain in signal-specific tables.
Prometheus API compatibility remains useful for native metrics and dashboards,
but it must not define the event query model.

Event-derived counts, rates, histograms, heatmaps, and percentiles are computed
from raw events or event aggregate states. They do not require conversion into
native metric samples unless a later interoperability feature needs it.

** Full-resolution acceptance and retention

Lighthouse does not silently sample accepted events. An event is accepted only
after a durable replay boundary, and accepted events remain reconstructable at
full resolution from immutable batches or their canonical archive. Producer
drops or upstream sampling must be reported; sampled events carry an explicit
sampling probability or weight. Approximate percentile, distinct-count, top-K,
or histogram functions may be used for interactive execution, but this changes
the aggregation algorithm rather than the retained data. Exact execution
remains available with cost guardrails or as an asynchronous job.

** Raw fallback

Attribute indexes, materialized aggregate states, and projections accelerate
supported query shapes. A query using an unmaterialized field falls back to raw
events rather than becoming invalid. Query responses must disclose whether an
aggregate is exact or approximate.

** Standard distributed data plane

Scale beyond one node with local =ReplicatedMergeTree= tables behind a
=Distributed= table. Initially shard by a stable hash of =tenant_id=, =dataset=,
and =event_id= so high-volume tenants use the whole cluster. Accept broad query
fanout until measurements show that its fixed cost or network use justifies a
virtual-partition placement layer. See
[[file:README.adoc][RFD 0001]].

** Bounded derived storage

Do not expand every attribute of every event into inverted index rows. Derived
tables must have a measured query benefit and a bounded amplification model.
Field-name and field-value discovery must use metadata catalogs rather than
array-joining the raw corpus at request time.

* Reference Evidence

** Honeycomb model

Honeycomb's current public model treats logs and spans as structured events
whose fields can be queried without a predefined schema. Native metrics use
dedicated metrics datasets and metric-specific operations. Its unified
experience therefore does not require one physical model for every telemetry
signal.

Relevant references:

- https://docs.honeycomb.io/get-started/honeycomb/traces-metrics-logs
- https://www.honeycomb.io/blog/introducing-honeycomb-telemetry-pipeline
- =experiments/000-gcp-parquet-corpus-profile.md=
- [[file:README.adoc][RFD 0001]]

** Scuba product model

Facebook's original Scuba system established the product and query model that
Lighthouse is targeting: self-describing structured events, arbitrary
slice-and-dice exploration, time series, histograms, percentiles, comparisons,
and drill-down to individual events. Its shared-nothing query path scanned all
time-relevant leaves, computed partial aggregates locally, and merged them
through a fanout tree. It intentionally used no general index beyond batch time
ranges and accepted sampling, short retention, and incomplete results to reach
sub-second latency.

Lighthouse adopts Scuba's flexible event exploration and storage-node partial
aggregation, but not Scuba's requirement choices around ingestion sampling,
memory-primary serving, short retention, or best-effort incomplete results.
Accepted events remain available at full resolution. If a bounded-latency query
omits unavailable data, the response must report freshness and coverage rather
than presenting the result as complete.

Relevant references:

- https://www.vldb.org/pvldb/vol6/p1057-wiener.pdf
- [[file:README.adoc][RFD 0001]]

** Supporting Meta-scale evidence

Kraken is not the Lighthouse product model; it is supporting evidence about
operating a later-generation analytics data plane at Meta scale. Its published
study ranged from 50 GB datasets with 1B records to a 150 TB dataset with 1.27T
records, more than 3,500 columns, and 8,192 shards. Flash-backed columnar blocks,
RAM caches, deterministic dataset partitions, and separation of storage
management from query serving show plausible later optimizations, but do not
establish that Lighthouse needs a custom virtual-partition control plane before
standard ClickHouse distributed fanout is measured.

Relevant reference:

- https://www.vldb.org/pvldb/vol15/p3522-mo.pdf

This evidence adds four architecture directions that require explicit
validation rather than being assumed from the single-node experiments:

- accepted events should enter a durable replay path before ClickHouse serving
  state, so serving tables can be reconstructed;
- immutable archived batches should contain enough canonical event and exact
  payload data to rebuild normalized tables;
- hot and archived data may need separate physical query paths behind one
  logical query contract rather than transparent part movement alone; and
- query diagnostics need independent aggregation-accuracy, input-completeness,
  and ingestion-freshness signals.

** Proof-of-concept findings

The proof of concept used typed nested key/value arrays, fingerprints,
attribute index tables, rollups, and alternate tail layouts. Its staging data
showed the principal failure mode to avoid:

#+BEGIN_SRC text
logs                         62.40M rows   10.55 GiB
logs_string_fingerprints      3.73B rows   69.42 GiB
#+END_SRC

The string fingerprint index had about 60 rows per source event. Broad metadata
queries still read tens to hundreds of GiB, timed out, or exceeded a 14.4 GiB
memory limit. A wide inverted index is therefore not a substitute for a raw
event layout, promoted fields, and bounded metadata catalogs.

The current 12-day corpus represents approximately 12.8 TB on this calibrated
scale. It can supply natural subsets for the 1 TB and 10 TB tests. A 100 TB test

** Lighthouse benchmark results to date

The architecture in this plan is grounded in the completed experiments, not
only in the Scuba workload model:

- Experiment 006 loaded all 547,356,173 rows (approximately 1.04 TB logical) to
  =Map= in 4.67 hours with 1.42 GiB peak insert memory and a 172.45 GiB table.
  Native =JSON= stopped at 63.2% after file-descriptor, part-count, inode, and
  free-space failures; a complete day projected to 206.2 GiB, 19.6% larger than
  =Map=. =Map= is therefore the selected long-tail serving representation for
  the MVP, rather than an open candidate among =JSON= and typed arrays.
- Experiment 007 showed why the raw representation cannot be the only
  interactive path. Promoted-column queries over the same day took 1.6-6.9
  seconds cold, while dynamic filters took 84-88 seconds and full-day heatmap
  and percentile queries took 77-95 seconds. Raw field discovery took 28
  seconds. These results require bounded catalogs, asynchronous exact scans,
  and derived dashboard paths rather than pretending every arbitrary query is
  instant.
- Experiment 008 added two configured dynamic-field indexes and aggregate
  states. The indexes occupied 3.06 GiB and all rollups about 4.4 MiB, for 1.78%
  derived-storage amplification. Dynamic filters improved from 83-85 seconds
  cold to 205-447 ms; rate, heatmap, and percentile fixtures improved from
  5-93 seconds to 6-33 ms. All 30 correctness checks passed. This supports a
  schema-stable, tenant-scoped acceleration registry, not indexing every field.
- Experiment 009 split one 547,356,173-row day into 104.23 GiB of normalized
  hot =Map= events and 72.95 GiB of exact payload on bulk storage, with matching
  row counts and checksums. Exact source lookup took about 12 ms on SSD and 351
  ms from bulk storage. This supports separate query-serving and exact-payload
  paths behind one logical event contract.
- Experiment 010 loaded and checksum-validated 5,689,254,359 rows across ten
  natural days and 240 hourly windows: approximately 10.81 TB logical input,
  1,000.85 GiB of normalized hot events, and 708.48 GiB of exact payloads. The
  combined physical representation is 16.98% of logical input, or 5.89×
  effective compression. At final capture the hot dataset retained 785 GiB of
  headroom. The run also validated resumability across truncation failures and
  an executor replacement, but its interrupted wall duration and concurrent
  bulk-pool writes are not production ingestion-throughput evidence.

* Draft MVP Event Contract

Instrumentation emits a versioned common envelope. Logs, spans, and application
events use the same acceptance and query path; =event_kind= controls validation
and rendering rather than selecting a separate store. The logical contract
contains at least:

#+BEGIN_SRC text
identity       tenant_id, dataset, event_id, immutable ingest_batch_id
time           source timestamp, observed timestamp
kind           event, log, or span
common fields  event name, service, environment, region, host, build, severity
trace context  trace ID, span ID, parent span ID, span kind, duration
dimensions     sparse string, boolean, and integer fields
measures       sparse integer and floating-point fields
sampling       sampling probability or weight when sampling occurred upstream
payload        exact canonical source event or immutable payload reference
schema         envelope and field-policy versions
#+END_SRC

The producer SDK and gateway contract is part of the data model. Producers must
batch and compress asynchronously, never block the application indefinitely,
report dropped events and backpressure, set source timestamps and stable event
IDs, and avoid sending known secrets or unrestricted request bodies. OpenTelemetry
is the default transport vocabulary, with a custom wide-event API where OTel's
signal APIs do not express the event cleanly.

The MVP ClickHouse serving table uses fixed columns for the routing and commonly
queried envelope plus =Map=-based long-tail attributes. Exact payload is kept in
the immutable archive and may also be retained in a separately ordered bulk
ClickHouse table for recent reconstruction. This is a physical implementation
of one logical event medium, not separate log and trace products.

The final DDL remains open only where the benchmarks have not decided it. Tests
must still determine:

- the number and boundaries of attribute namespaces;
- the correct timestamp bucket in the sorting key;
- whether =service_name= belongs before or after the time bucket;
- the best ClickHouse representation for event and trace identifiers;
- which GCP and OpenTelemetry fields deserve fixed or materialized columns;
- how logical dimension and measure types are preserved alongside the selected
  =Map= serving representation;
- appropriate partition granularity, retention behavior, and archive format;
  and
- whether payload lookup remains a ClickHouse bulk table, moves to direct object
  retrieval, or uses both by retention window.

Multi-tenancy does not imply one promoted column per tenant field. Fixed or
materialized columns are reserved for common envelope fields or fields with
exceptionally broad, measured benefit. Tenant-specific equality acceleration
uses the schema-stable =(tenant_id, dataset, field_name, field_value, timestamp,
event_id)= shape validated in Experiment 008; tenant-specific dashboard
rollups likewise store configured dimensions as data. This allows different
tenants to accelerate different fields without divergent ClickHouse DDL.

* Query and Storage Architecture

This architecture is a proposed MVP, not an accepted final design. It separates
three concerns so that the interactive ClickHouse copy can be rebuilt and
tenant policy can evolve without placing a metadata lookup on every event:

#+BEGIN_SRC text
OTel / wide-event SDKs
          |
          v
stateless ingestion gateways <----- cached, versioned tenant policy
          |
          v
durable Kafka/Redpanda acceptance boundary
          |---------------------> immutable canonical batch archive
          |
          v
normalization consumers -------> ClickHouse local ReplicatedMergeTree tables
                                  behind a Distributed table
                                             |
                                             v
                                  query planner and Scuba-style UI

stream copy ---> field/cardinality sketches ---> metadata and policy registry
query history ---------------------------------> acceleration recommendations
#+END_SRC

** Ingestion plane

Stateless Lighthouse gateways authenticate tenant and dataset, validate the
versioned envelope and field types, enforce event/string/field-count limits,
redact or reject classified data, and apply tenant byte/event quotas. Gateways
use cached, versioned policy snapshots so control-plane unavailability does not
turn into a per-event database dependency. Policy versions are recorded with
accepted batches.

The durable transport is the acceptance boundary. Acknowledgement, retry, and
duplicate semantics must be explicit; stable event IDs and immutable batch IDs
make idempotent consumers and replay possible. ClickHouse serving consumers and
the canonical archive consumer advance independently. Queue lag and archive
lag are visible separately from ClickHouse query freshness.

** Durable ingestion and rebuild

Treat ClickHouse as the query-serving copy rather than assuming its local parts
are the only source of truth. The production design should acknowledge accepted
events through a durable replay boundary, assign immutable event and batch
identities, and persist canonical batches to an economical archive. ClickHouse
and optional accelerators consume this stream and must be reconstructable from
the archive plus replay position.

The ten-day benchmark's bulk =event_payloads= table measures the immediate
storage and lookup tradeoff; it is not by itself a final durable log or object
archive design. Record the acknowledgement, retry, deduplication, replay, and
archive-format contracts in a separate decision before production ingestion is
implemented.

** Primary raw path

The normalized hot table optimizes tenant, dataset, time, and common
service-scoped reads. Its dynamic attributes are the exact normalized fallback
for every supported event query. Exact source reconstruction joins or fetches
the separately retained canonical payload only when requested; normal filters
and aggregations do not pay payload I/O.

** Distributed execution path

Use a local MergeTree table per shard and expose one ClickHouse =Distributed=
table as the initial cluster-wide query path. A stable hash over tenant,
dataset, and event identity spreads large tenants across all shards. Local
servers scan and compute mergeable partial aggregates; the initiating server
merges those states.

The initial design deliberately sends tenant/dataset/time queries to every
shard. Adding shards does not require immediate historical redistribution:
queries remain correct across all shards, new events use the expanded topology,
and old placement converges through retention. Measure fanout latency and
network traffic before adding virtual partitions, targeted routing, or a custom
placement service.

** Trace path

Add a narrow projection or derived trace table ordered by tenant and trace ID.
It should contain enough fields to render a waterfall and identify correlated
logs without duplicating every dynamic attribute. Benchmark projection storage
and trace-fetch latency before choosing projection versus table.

** Metadata catalogs

Maintain a small versioned registry for datasets, field definitions, privacy
classification, retention, quotas, and accelerations. A stream consumer, not
the ingestion gateway, maintains bounded time-aware observations for:

- known field names and observed types;
- field presence and last-seen time;
- approximate distinct counts using mergeable sketches;
- bounded top-K values and value-size distributions;
- type conflicts and cardinality growth rates; and
- promoted, indexed, and aggregated fields with coverage watermarks.

High-cardinality values such as event, trace, span, request, account, or run IDs
must not be enumerated for broad autocomplete. Their events are still retained
and exact filtering remains possible; cardinality governance limits metadata,
group result size, and acceleration cost rather than deleting accepted data.

Per-tenant and per-dataset policies bound event bytes, field count, field-name
growth, string length, indexed fields, derived bytes, groups returned, scan
bytes, query memory, and concurrent work. A cardinality spike creates a visible
policy event and may stop new acceleration or expensive grouping, but must not
silently sample already accepted events.

** Dashboard aggregate states

Materialized dashboard tables may store mergeable states such as:

#+BEGIN_SRC sql
countState()
sumState(duration_ns)
minState(duration_ns)
maxState(duration_ns)
quantilesTDigestState(0.5, 0.9, 0.95, 0.99)(duration_ns)
#+END_SRC

Initial rollups cover only saved dashboards and measured repeated workflows.
Experiment 008 shows that this can reduce 5-93 second raw aggregate fixtures to
6-33 ms with only about 4.4 MiB of aggregate states on the measured day. Do not
construct a cube over every dynamic attribute. Unsupported groupings use the
normalized raw table.

Acceleration creation is asynchronous and disposable:

1. A dashboard explicitly requests required aggregate states.
2. Query history may recommend an equality index or aggregate for an expensive,
   repeated tenant-field shape and estimate its build and storage cost.
3. Activation is manual initially; later automatic activation is permitted only
   within tenant field-count, cardinality, storage, and backfill-CPU budgets.
4. The planner uses an acceleration only inside its complete coverage watermark
   and falls back to raw execution elsewhere.
5. Unused accelerations expire without changing or expiring accepted events.

** Exact and approximate modes

- =auto=: use mergeable approximate states or raw approximate functions when
  they satisfy the query.
- =exact=: execute against full-resolution values with stricter cost limits.
- =raw=: force raw-event execution for validation and forensic workflows.

Exact and approximate results must be clearly identified in API responses and
query diagnostics.

Mathematical accuracy, input completeness, and freshness are independent. Every
response reports the execution mode, data watermark, expected and participating
shards or partitions, scanned events/bytes, and whether upstream sampling
weights were applied. Alerts, billing, security, or compliance workflows may
require complete execution even when an interactive exploration permits a
clearly labeled bounded-latency partial result.

** Storage tiers

The MVP uses normalized events on ClickHouse's fast serving tier and immutable
canonical batches on economical bulk or object storage. Experiment 009 validates
the immediate physical split and exact lookup, but its bulk ClickHouse payload
table is not itself the final durability design. Querying archived normalized
events through ClickHouse object-backed parts versus a distinct archive executor
remains an experiment; either path must preserve one logical query contract and
report its source, freshness, and completeness.

** Query and exploration plane

The planner requires tenant, dataset, and bounded time range, then chooses raw,
trace, metadata, attribute-index, aggregate-state, or archive execution. It
pushes mergeable partial aggregation to ClickHouse shards and returns raw rows
only for a bounded event sample or explicit reconstruction request. Deadlines,
cancellation, concurrency limits, maximum scans/groups/result rows, and workload
priority protect dashboards and tenants from one another.

The MVP user workflow is Scuba-style rather than SQL-first: compare periods,
add or remove filters, group by a field, view top values/cardinality before an
expensive grouping, inspect time series/heatmaps/percentiles, and drill into
representative exact events. Saved queries and dashboard panels use the same
query contract and expose approximation, freshness, coverage, and upstream
sampling indicators.

** Privacy and operational instrumentation

Field classification, secret/token detection, PII redaction or hashing,
tenant isolation, field-level access, query audit logs, and deletion workflows
must be designed before broad producer adoption. Arbitrary headers, request
bodies, SQL parameters, and authentication material are rejected or redacted by
default rather than relying on short retention after collection.

Lighthouse must expose telemetry outside its own serving path for at least:

- events received, accepted, rejected, dropped, and upstream-sampled;
- bytes and field counts by tenant and dataset;
- producer-to-durable, durable-to-archive, and durable-to-query lag;
- malformed events, type conflicts, policy versions, and replay backlog;
- cardinality, field-name growth, value sizes, and top-K churn;
- hot and archive bytes, parts, merges, retention, and acceleration coverage;
- query queue and execution latency, scans, groups, memory, cancellation, and
  timeouts; and
- response freshness, shard coverage, accuracy mode, and partial-result rate.

The telemetry system will become production-critical, so its minimum health,
durability, and alerting signals cannot depend exclusively on Lighthouse.

* Benchmark Volume Definition

Each test records three independent byte measurements:

1. =logical_input_bytes=: GCP-equivalent pre-index event bytes. This defines the
   1 TB, 10 TB, and 100 TB test levels.
2. =clickhouse_uncompressed_bytes=: =system.parts.data_uncompressed_bytes= for
   the internal columnar representation.
3. =physical_bytes=: =system.parts.bytes_on_disk= summed across base tables,
   indexes, projections, and derived tables.

Report:

#+BEGIN_SRC text
base compression ratio      = logical_input_bytes / base_table_physical_bytes
storage amplification       = all_physical_bytes / base_table_physical_bytes
effective physical ratio    = logical_input_bytes / all_physical_bytes
#+END_SRC

Volume and ingestion rate are separate benchmark axes. A retained 100 TB corpus
must be tested while ingestion continues at representative rates rather than
only as a static database.

Provisional daily-rate targets at 1.9 KB/event are:

#+BEGIN_SRC text
500M events/day       5,787 events/sec       ~0.96 TB/day
1B events/day        11,574 events/sec       ~1.9 TB/day
3B events/day        34,722 events/sec       ~5.8 TB/day
#+END_SRC

* Corpus Scaling Method

- Select natural, contiguous event-time subsets for 1 TB and 10 TB.
- Preserve the original distribution, width, nullability, and attribute
  cardinality during schema comparisons.
- Build 100 TB by replaying the complete corpus into distinct shifted daily
  partitions.
- Regenerate timestamps and event IDs for each replay.
- Rotate or regenerate selected naturally changing high-cardinality dimensions,
  such as pod, task, and instance IDs, so long-retention cardinality does not
  remain artificially fixed.
- Keep the same transformed corpus for every physical design under comparison.
- Record that repeated body distributions remain a limitation of the synthetic
  100 TB corpus.
- Do not benchmark with exact duplicate inserts in the same time partition.

* Representative Query Inventory

Every physical design must run the same parameterized inventory:

1. Recent unscoped tail by dataset and time.
2. Recent tail scoped by service and severity.
3. Body token/text search.
4. Exact filter on a promoted low-cardinality field.
5. Exact filter on a dynamic low-cardinality field.
6. Exact lookup on a dynamic high-cardinality identifier.
7. Multiple dynamic-field conjunction with mixed selectivity.
8. Field-name discovery.
9. Allowed field-value discovery.
10. Trace waterfall lookup by trace ID.
11. Trace lookup including correlated logs.
12. Count/rate time series over a promoted grouping.
13. Duration heatmap over a promoted grouping.
14. Approximate p50/p90/p95/p99 over a promoted grouping.
15. Approximate percentile grouped by an arbitrary dynamic field.
16. Exact percentile over a bounded raw window.
17. High-cardinality arbitrary group-by with planner guardrails.
18. Standard dashboard query set under concurrent ingestion.
19. Concurrent dashboard and exploratory workloads.
20. Cold/object-storage versions of selected exploration queries.

Each run records:

- cold and warm latency, including p50 and p95 over repeated runs;
- rows and bytes read;
- peak query memory;
- result rows and correctness checksum;
- selected parts, granules, indexes, and projections;
- CPU time and query concurrency;
- background merges, pending parts, and ingest lag;
- physical bytes for every supporting schema object.

Latency, concurrency, freshness, retention, and ingestion acceptance thresholds
must be agreed before this draft becomes the MVP contract and before the 10 TB
query validation. Relative improvement alone is not a product acceptance
criterion.

* Decision Gates

** After 1 TB

The benchmark-selected event attribute representation is =Map=. Record its base
sort key, partitioning, identifier representation, trace access path, and
initial promoted columns. Do not proceed with the rejected native =JSON= or
typed-array candidates at 10 TB.

** After 10 TB

Confirm that the chosen schema, dashboard materializations, metadata catalogs,
and query planner meet product thresholds without unbounded storage
amplification. Size the physical environment required for 100 TB.

** After 100 TB

Decide the production sharding, replication, storage-tier, workload-isolation,
and recovery architecture. Treat 1 PB as a separate distributed-systems test,
not a linear extrapolation.

* Draft MVP Exit Criteria

RFD 0001 remains in discussion. The MVP contract is ready to commit only when:

- Experiment 011 reaches a documented terminal result and its multi-day query,
  restart, and workload-isolation evidence is incorporated;
- the user workflow and p50/p95 latency, freshness, retention, concurrency, and
  cost targets are explicit;
- acceptance, retry, deduplication, archive, and replay semantics are decided;
- cardinality and privacy defaults have concrete per-tenant budgets and
  observable rejection behavior;
- one service can emit the versioned envelope, replay into a clean serving
  table, and prove event/payload checksums;
- raw, accelerated, approximate, and incomplete responses expose consistent
  diagnostics; and
- the comparison, group-by, histogram, percentile, and exact-event drill-down
  workflow has been tested with an operator rather than inferred from SQL
  benchmarks alone.

* Open Questions
