== Question

Which cloud or dedicated-host deployment meets Lighthouse's ingestion,
interactive-query, retention, durability, and degraded-operation requirements at
the lowest total cost per retained logical TB and accepted event?

== Principle

Production performance is a workload and topology property, not an instance
benchmark. Compare providers using the same immutable corpus, ClickHouse build,
schema, shard expression, retention, replication semantics, query fixtures,
concurrency, ingestion replay, failure tests, and result validation.

Do not compare a replicated production candidate on one provider with an
unreplicated cache on another. Do not call the highest short-lived throughput
production capacity. A candidate passes only at a sustained operating point
with safety headroom and the required degraded behavior.

== Candidate deployment classes

Select current instance generations and prices immediately before provisioning;
do not freeze family names in the RFD.

. *AWS self-managed:* storage-optimized EC2 with local NVMe for hot serving,
   S3 for durable batches and exact payload, and same-AZ then cross-AZ replica
   layouts.
. *GCP self-managed:* storage-optimized Compute Engine or suitable
   general-purpose compute with Local SSD, Cloud Storage durability, and
   equivalent zonal and multi-zone layouts. This candidate must include the
   avoided-egress benefit when source telemetry already originates in GCP.
. *Azure self-managed:* local-NVMe storage-optimized virtual machines with
   Blob Storage durability and equivalent zone placement.
. *Dedicated or bare-metal providers:* current offerings from providers such
   as Hetzner or OVHcloud when they provide sufficient NVMe, memory, network,
   region, replacement, and object-storage behavior. Lower rental cost must be
   weighed against weaker elasticity, slower replacement, and operational
   responsibility.
. *Managed ClickHouse:* ClickHouse Cloud or another credible managed
   ClickHouse service as an outcome-level comparison. Its object-storage and
   compute architecture need not match self-managed local NVMe, but it must run
   the same product workload and disclose available settings, scaling events,
   storage, transfer, and service cost.
. *Current owned host:* use the completed local measurements as a calibration
   and amortized-cost reference, not as production availability evidence.

Compare x86 and ARM only when the same ClickHouse version, query semantics, and
operational tooling are supported. Spot or preemptible capacity may prepare or
transform data, but measured latency and soak runs use non-interruptible
capacity unless interruption is itself the tested production policy.

=== Provisioning approval packet

Before any Stage A resource is created, record and obtain approval for:

. the cloud project and billing account, region, and hard dollar allowance;
. the database and load-generator shapes and maximum wall-clock lifetime;
. automatic teardown independent of benchmark success;
. budget alerts and labels identifying the experiment and owner;
. whether the source corpus is permitted to leave the current machine and, if
  so, its approved bucket, region, encryption, retention, and deletion policy;
. a redacted or synthetic corpus when the production-derived Parquet data is
  not approved for cloud upload; and
. the exact resources in an OpenTofu plan, including boot disks, object storage,
  IP addresses, and estimated network transfer.

Stage A must not depend on a publicly reachable ClickHouse port. Put the
database and load generator on a private VPC, restrict SSH or IAP access, and
run the query driver from the dedicated load generator. Local NVMe is
disposable serving state; the immutable corpus and run artifacts require a
separate approved durable location.

== Staged test matrix

=== Stage A: provider calibration

Run the same approximately 1 TB logical natural day on one storage-optimized
leaf from each serious candidate. Use this inexpensive gate to compare:

- load and merge behavior;
- local hot-table compression;
- narrow and full-day raw queries;
- configured indexes and aggregate states;
- local NVMe or block-storage throughput and latency; and
- observed cost for the measured wall duration.

Eliminate candidates that cannot meet single-leaf correctness, operational, or
price/performance requirements. Do not run every provider at 10 TB merely to
produce a broad comparison table.

=== Stage B: actual horizontal scaling

For finalists, load the immutable 5.69B-row, 10.81 TB logical corpus and compare:

[source,text]
----
1 shard x 1 replica
2 shards x 1 replica
4 shards x 1 replica
----

This stage measures real network fanout, leaf-local partial aggregation,
coordinator reduction, shard skew, and scale efficiency without replication
overhead obscuring the trend.

=== Stage C: production candidate

Run the likely production topology, initially expected to be approximately:

[source,text]
----
4 shards x 2 replicas
2 query coordinators or equivalent query entry points
durable stream and immutable object archive
local-NVMe hot serving tier
object-backed exact payload and replay tier
----

Test a low-latency same-zone placement baseline, then the intended failure-domain
layout with replicas separated across zones. Record replication lag, cross-zone
bytes and cost, insert acknowledgement latency, and replica selection behavior.

=== Stage D: 24-to-72-hour soak

Replay the source's timestamp distribution at observed rate, twice expected
rate, burst rate, and the provisional 1B- and 3B-events/day targets. Run
dashboard, exploration, incident-burst, bounded drill-down, and expensive exact
workloads concurrently while inserts, merges, aggregate maintenance, payload
archival, retention, and replica catch-up operate.

== Workload and SLO gates

Define exact freshness, p50/p95/p99 latency, concurrency, retention, and cost
limits before provisioning Stage B. At minimum, measure independently:

- dashboard aggregate-state refreshes;
- narrow interactive event exploration;
- selective and prevalent attribute predicates;
- latest-event and trace retrieval;
- exact payload retrieval;
- guarded raw fallback and asynchronous exact work; and
- mixed workloads with dashboard isolation.

Ramp each workload until query latency, ingestion freshness, merge backlog,
memory, disk, or network violates its threshold. Production capacity is the
highest sustained operating point that also passes required N-1 behavior, not
the saturation point. Initial sizing should retain substantial safety headroom,
subject to measured failure capacity rather than a fixed universal percentage.

== Failure and recovery tests

- Stop one replica and measure query behavior, write availability, lag, and
  catch-up.
- Remove one complete shard and verify complete queries fail while explicitly
  bounded partial queries disclose coverage.
- Slow one leaf and verify deadlines, cancellation, and coordinator limits.
- Terminate a coordinator and verify client retry and query identity behavior.
- Rebuild a replica from the chosen authoritative source and measure network,
  time, and serving impact.
- Delay the stream consumer and replay immutable batches without duplication.
- Exercise object-store throttling or delayed exact-payload retrieval.

Critical SLOs must be evaluated with the required failure margin. A topology
that passes only when every node is healthy is not production capacity.

== Cost model

Capture actual metered and listed cost for the test interval, normalized as:

- cost per retained logical TB-month;
- cost per billion accepted events;
- cost per million dashboard and exploratory queries at the target SLO;
- hot serving, replicas, coordinators, stream, and object archive separately;
- cross-zone and cross-region network traffic;
- source-cloud egress, especially for the approximately 32 TB/month GCP-origin
  telemetry workload;
- object requests, retrieval, and lifecycle transitions;
- backup, observability, load-generation, and idle headroom; and
- rebuild and failure-test transfer cost.

Cross-cloud source egress can dominate a cheaper compute quote. Report both a
same-cloud deployment and any cross-cloud alternative using the actual source
location and expected monthly transfer. Managed-service cost should include its
operational benefit explicitly but remain separate from measured infrastructure
spend; do not invent a precise engineering-labor adjustment.

For dedicated hardware, include amortized server cost, power, rack, network,
spares, replacement time, and realistic utilization. For cloud, show on-demand
test cost and production scenarios using then-current committed-use or reserved
discounts without applying those discounts to short benchmark invoices.

== Reproducibility

Provision self-managed candidates with OpenTofu or Terraform and install the
Nix-pinned ClickHouse closure. Record:

- provider, region, zone, instance generation, CPU architecture, memory, local
  disks, network limits, and placement policy;
- image, kernel, filesystem, RAID, mount, and CPU-affinity settings;
- ClickHouse version, configuration, schema, and benchmark revision;
- shard, replica, coordinator, stream, and object-store topology;
- corpus manifest, checksums, transformation, and load distribution;
- warm, ClickHouse-cold, restart-cold, and cache policies;
- raw provider billing export or cost report for the test interval; and
- repeated runs on fresh capacity where host variance could change a decision.

Use a separate load-generator instance or pool so query clients and ingestion
drivers do not consume database resources. Preserve raw query logs, system
metrics, host metrics, result hashes, coverage metadata, and infrastructure
plans with secrets removed.

== Decision gates

- Stage A selects at most a small number of finalists based on correctness,
  operability, and price/performance.
- Stage B selects a topology only when scaling efficiency and coordinator cost
  are measured rather than extrapolated.
- Stage C selects a production candidate only when replication and failure-
  domain placement pass.
- Stage D determines sustained production capacity and cost with headroom.
- The later 100 TB validation uses the selected candidate or explicitly records
  why a different architecture is required.

== Guardrails

- Obtain explicit approval for the estimated budget before provisioning each
  stage.
- Apply provider budget alerts, resource tags, automatic expiration, and a
  complete destroy plan before starting.
- Never upload unredacted source telemetry without confirming data
  classification, region, encryption, and access policy.
- Do not publish datasets, credentials, infrastructure addresses, or billing
  exports in public run artifacts.
- Stop after a failed decision gate instead of completing an expensive matrix
  with a non-viable candidate.

This Stage A run supports the MVP's bounded-acceleration architecture: retain
full-resolution `Map` events for arbitrary fallback, add tenant/dataset-scoped
attribute indexes only for observed selective predicates, and maintain small
mergeable aggregate states for known dashboard shapes. It does not yet select
GCP as the production platform. Spot interruption invalidated the planned
three-repetition acceleration variance sample and demonstrates that
interruptible load generators need resumable orchestration; Stage B production
latency and soak tests must use non-interruptible leaves unless preemption is
the behavior under test.

The run did not preserve a metered billing export. Its exact observed spend and
normalized cost remain unresolved, so it has not passed Experiment 015's
price/performance decision gate. Obtain the billing line items after provider
reporting settles before comparing this run with another provider.

=== Stage B corpus correction and execution design

The first Stage B upload selected `2026-07-15` through `2026-07-24` under the
incorrect assumption that those directories were the 5.69B-row corpus used by
Experiments 010 through 012. Direct Parquet-footer inspection disproved that
assumption before compute provisioning: the July set contains 5,031,393,957
rows and represents approximately 9.56 TB logical at the provisional 1,900
bytes per event, not the required 5,689,254,359 rows and 10.81 TB. Its 2,305
objects and 1,150,144,512,878 physical bytes were uploaded correctly, but it is
not the immutable comparison corpus and must not be used for Stage B results.

The corrected corpus is the exact Experiment 010 input, `2026-08-01` through
`2026-08-10`. The already validated `2026-08-05` Stage A objects are reused;
the other nine days were uploaded from 2026-09-12T22:34:02Z through
2026-09-13T02:08:20Z and independently checked against the versioned
`stage-b/corpus.tsv` inventory. All ten per-day counts and byte totals match:
2,245 Parquet objects, 1,116,601,405,252 physical bytes, and 5,689,254,359
footer-reported rows. Ten SHA-256 manifests are present in the private bucket.
The July objects remain private and subject to the bucket lifecycle while this
correction is reviewed; removing them early is optional cleanup rather than a
benchmark prerequisite.

Stage B runs 1-, 2-, and 4-shard topologies sequentially so every topology sees
the same complete corpus without retaining three physical table copies at
once. Each leaf is an on-demand `z3-highmem-14-standardlssd` with one disposable
3,000 GiB Titanium SSD. A dedicated on-demand coordinator and load generator
prevent Spot preemption from invalidating latency samples or interrupting the
day-bounded loader. All VMs have auto-deleting boot disks and a provider-enforced
36-hour default lifetime, bounded in configuration to 12 through 48 hours.

The loader streams private GCS Parquet objects through `clickhouse local`,
applies the same normalization as the local benchmark, and synchronously
inserts through a `Distributed` table sharded by
`cityHash64(tenant_id, dataset, event_id)`. Every completed immutable source
batch is validated against its cumulative row count and normalized-event
checksum. Resume accepts only a complete matching batch and refuses an
ambiguous partial batch without deleting data. Completed-batch markers and
final evidence are written to the private artifact prefix.

The first corrected Stage B load disproved the assumption that a corpus source
directory is also an event-time partition. While loading source directory
`2026-08-01`, valid event timestamps crossed into `2026-08-02`; at 538,992,628
total rows, 5,168,109 rows were already in the latter partition. Dropping or
validating `toDate(timestamp) = source_directory` would therefore reject valid
data and could delete rows belonging to an adjacent source batch. Stage B now
validates the cumulative row count and normalized-event checksum after each
immutable source-directory batch. It recovers a completed batch only when the
entire cumulative state matches and refuses an ambiguous partial batch without
deleting event-time partitions. Final validation still checks the complete
5,689,254,359-row corpus. This preserves the query-serving schema while making
the distinction between source batches and event-time partitions explicit.

That same validation then rejected the complete 638,620,872-row batch because
its normalized checksum was 16,518,503,113,489,990,414 rather than the retained
11,307,978,330,555,646,774. Row-level comparison against the Experiment 010
table found the concrete difference: inferred Parquet input typed `labels` and
`resource_labels` as `Nullable(JSON)`, so conversion through the transform's
string-oriented extraction retained only `gcp.resource.type` and silently lost
the label and resource-label maps. The local loader had explicitly declared
both columns as `Nullable(String)`. Stage B now uses that same complete input
structure rather than ClickHouse Parquet inference. A 100-row transform check
reproduced the retained labels and resource labels before the invalid cloud
batch was removed and rebuilt. The rejected batch is not benchmark input.

The next corrected attempt stopped after 99,775,762 rows when one concurrent
`gcloud storage cat` process transiently reported that no active account was
selected. Its empty output then surfaced as an empty Parquet file and an empty
ClickHouse insert. The VM's attached service account and active gcloud account
were both present immediately afterward, so the observed cause is a transient
gcloud streaming failure rather than expired VM credentials. The loader now
downloads each object completely to a worker-private temporary file with three
bounded attempts before transformation. This intentionally adds load-generator
disk I/O, but prevents a failed or partial object stream from reaching the
serving table. Temporary files are removed on both success and failure.

The cloud-stage continuation is a separate guarded process rather than an
unconditional shell chain. It waits for the loader's `completed` state, runs the
raw query inventory, then builds and measures accelerations. A failed load never
starts queries, and a failed phase prevents the next phase. The continuation
archives successful or failed stage evidence to the private artifact prefix so
the cluster does not sit idle waiting for an operator between phases.

The first full one-shard load attempt exposed a Native-format schema mismatch
on 2026-09-13. All 638,620,872 rows for August 1 were accepted in 2 hours 20
minutes, but end-of-day validation found zero rows in the expected date. Direct
table inspection showed every row in partition `1970-01-01`: the transformation
emitted `event_timestamp`, while the serving table names that field `timestamp`,
so Native name matching supplied the destination column's zero default. The run
is invalid performance evidence and remains preserved as a failed run. The fix
aligns the emitted name with the destination schema and adds a first-batch
partition check, reducing recurrence detection from a full day to one batch. A
100-row Parquet-to-Native-to-MergeTree round trip then retained the expected
2026 timestamp range and contained zero epoch timestamps.

This is process- and day-resumable, not Local-SSD durable after VM loss. Spot
leaves are therefore invalid for the retained Stage B topology. The immutable
GCS corpus remains the replay boundary if an on-demand leaf is lost.

URI scheme instead of assuming Google Cloud.

This is a hardware change, so the accepted GCP one-shard result is not a
same-hardware baseline for a two- or four-shard AWS run. The AWS matrix
therefore starts with its own one-shard topology, and scaling efficiency is
measured within one hardware generation. The GCP one-shard result keeps its
role as the accepted Stage B baseline and as the source of the measured phase
timings the AWS estimate is built from.

=== AWS Stage B topology and guardrails

The AWS fleet is `shard_count` (1, 2, or 4) `i4i.4xlarge` serving leaves, one
`m7i.xlarge` coordinator, and one `m7i.4xlarge` load generator in a single
availability zone. A leaf carries 16 vCPU, 128 GiB RAM, and a 3,750 GB
instance-store NVMe volume.

The leaf shape follows from the accepted one-shard measurement rather than from
convenience. That run left 1,400.6 GiB of hot parts plus 31.8 GiB of derived
parts, with a 108.3 GiB largest part and a 150 GiB merge cap, so a leaf has to
hold roughly 1,582 GiB before any reserve. The 1,875 GB `i7i.2xlarge` would sit
at 90.6% full and would also halve the leaf vCPU count, which would confound the
scaling measurement; `i4i.4xlarge` sits at 45.3%.

EC2 has no provider-enforced `max_run_duration`, so the lifetime ceiling is
enforced from outside the fleet. Every node schedules its own `shutdown -h` from
user data, the topology sets `instance_initiated_shutdown_behavior =
"terminate"`, and a scheduled watchdog Lambda independently terminates any
instance tagged `experiment=015` that outlives the declared lifetime plus a
grace period, whatever state its operating system is in. The watchdog's IAM
policy is tag-conditioned, so it cannot terminate anything outside the
experiment even if its own filters were wrong. A monthly account-wide budget
adds forecasted and actual alerts and a stop action; the ceiling is account-wide
because cost allocation tags need 24 hours to activate, which is longer than a
topology lives.

Cost controls that are not fixed by the experiment: single-AZ placement so no
traffic is billed cross-AZ; a public subnet only so Session Manager and package
mirrors work without a NAT gateway; a free S3 gateway endpoint for corpus reads
and result writes; ClickHouse state on instance-store NVMe so no EBS data volume
is provisioned; on-demand capacity only, because Spot would invalidate a
multi-hour run by losing serving state; and a 45-day bucket expiry that removes
a forgotten corpus without an operator.

=== AWS Stage B image defect and fix

The first AWS image, `ami-0c18a88f454bbc3af`, was unbootable. The smoke test
that caught it applied the real Stage B module at one shard with a twelve-hour
lifetime ceiling, which created ten resources including the budget stop action,
and then launched the fleet.

Every instance failed in the same way: none registered with Session Manager,
EC2 instance status checks went `impaired` and never recovered, network output
stayed at zero, and the cached console output was empty. A minimal `m7i.large`
probe launched from the same image in the default VPC with no user data, no
benchmark security group, and no module involvement failed identically, which
isolated the fault to the image rather than to the VPC, subnet, security group,
instance profile, or user data.

`aws ec2 get-console-output --latest` then gave the cause directly:

[source,text]
----
[    9.371873] systemd[1]: System cannot boot: Missing /etc/machine-id and /etc is mounted read-only.
----

The provisioner generalized the image with
`cloud-init clean --logs --machine-id`. That flag removes the machine identity,
and Debian 12's systemd refuses to boot when `/etc/machine-id` is missing while
`/etc` is still read-only during early boot. The instances never reached
`network-online.target`, so the Session Manager agent never registered, the
benchmark startup script failed, and the node was unusable. The GCP provisioner
keeps `--machine-id` and boots correctly under Google's guest environment, so
its recipe is unchanged.

The fix is one line: the AWS provisioner now runs `cloud-init clean --logs`
only, and the first boot regenerates the identity, which is what an EC2 image is
expected to do. Two smaller lessons are folded into the tooling: the evidence
collector now requests `--latest` console output, because the cached form is
empty for an instance whose console has never been polled, and this record
confirms the value of the smoke test, since the same fault would otherwise have
surfaced only after the fleet was provisioned for a paid run.

Failure cleanup: the unbootable image was deregistered and its snapshot deleted,
the smoke topology was destroyed with all ten resources, and the probe instance
was terminated. The failed attempt cost about $0.95 of metered usage: roughly
46 minutes of `m7i.large` builder, 21 minutes of the three-node fleet, 8 minutes
of probe, and their gp3 volumes.

=== AWS Stage B bootstrap defects and the passing smoke test

The rebuilt image booted and registered all three nodes with Session Manager,
but the first smoke test still failed: `/mnt/disks/clickhouse` was unmounted and
the ClickHouse service was inactive. The node's own startup log named the cause:

[source,text]
----
expected exactly one instance-store device, found 3
----

AWS publishes three by-id aliases for a single instance-store device: a plain
name, a `-ns-1` namespace alias, and a `_1` alias, all resolving to the same
`/dev/nvme1n1`. The leaf counted three devices, failed its exactly-one
assertion, and exited before formatting or mounting anything. The aliases are
now resolved and deduplicated before counting, and the detection has a table
test covering one device, two real devices, and none.

Three further defects surfaced in the same round and are fixed together:

- The readiness probe activated the Flox environment while systemd was
  activating it for the server. Two concurrent first activations race on the
  activation state directory, and the loser exits with `EACCES`, which restarted
  the server twice before it settled and left the node without its `READY`
  marker. The binary is now resolved once and reused, the unit gets a runtime
  directory so Flox has a writable activation root, and the evidence collector
  does the same. This also explains why the same recipe worked on GCP, where the
  runtime directory exists.
- Changing `user_data` stopped and started the instances rather than replacing
  them, and cloud-init runs its per-instance modules once, so the node silently
  kept running its old bootstrap and the first fix appeared not to work.
  `user_data_replace_on_change` now forces a real replacement.
- The evidence collector's remote command referenced a variable without escaping
  it inside an unquoted here-document, so the local shell would have expanded it
  to nothing before the command ever reached the node. ShellCheck caught it.

The final smoke test passed: all three nodes registered with Session Manager,
`NRestarts=0` with the service active, `READY` and `hardware.txt` written, the
3.4 TB instance store mounted at `/mnt/disks/clickhouse`, ClickHouse answering
`26.8.2.7`, `SELECT 1` succeeding from the load generator to the coordinator and
from the coordinator to the leaf, the coordinator's `remote_servers` naming the
leaf, and the evidence collector returning a checksummed bundle for all three
nodes with no console fallback. The smoke topology was then destroyed, leaving
no instance and no volume behind.

The three smoke rounds together cost roughly $2 of metered usage, which is the
price of finding all four defects before a paid run rather than during one.

=== AWS Stage B first load attempt failed on a byte-formatting bug

The first AWS phase started at 2026-09-15T21:49:19Z and failed its very first
gate. The loader's own failure record named it exactly:

[source,text]
----
reason=corpus-mismatch
exit_code=1
line=218
command=return\ 1
----

and the log line showed why:

[source,text]
----
2026-08-01 corpus mismatch: expected 224/113283993214, found 224/1.13284e+11
----

The object count was correct and the byte total was the same number written in
scientific notation. Debian ships `mawk`, whose `print` renders a large integer
that way, while the development machine's `gawk` prints it exactly; the shared
object-store helper summed object sizes with `awk ... { print total }`. The gate
was right to fail: a byte total that does not compare equal to the inventory
cannot be trusted. The helper now uses `printf "%.0f"`, which is unambiguous
across implementations, and the same latent bug in the GCS path — introduced by
the object-store refactor, which converted the leading integer to a number
instead of printing it as a string field — is fixed with it.

The guarded continuation behaved as designed: it saw the loader fail, recorded
`load-failed`, and uploaded its failure archive instead of proceeding to the
query matrix. Two further defects were found and fixed before the retry: nodes
could not read the staged benchmark revision because `results/` was write-only,
and the runbook used `bash -lc` inside `flox activate`, where a login shell
re-sources `/etc/profile` and wipes the `PATH` the activation just set.

Re-verification after the fix is stronger than the sampled check it replaces:
every one of the ten uploaded days was compared against the committed inventory
and all ten match on object count and byte total, 1,116,601,405,252 bytes in
total. The failed attempt cost about a minute of the three-node fleet.
