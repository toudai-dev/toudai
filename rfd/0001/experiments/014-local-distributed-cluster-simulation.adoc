== Question

Can Lighthouse use ClickHouse's standard `Distributed` engine with stable
event-hash sharding while keeping fanout latency, coordinator work, shard skew,
query correctness, and failure semantics observable and bounded?

== Scope

Run one coordinator and multiple native ClickHouse leaf processes on this host,
each with isolated ports, data, temporary, user-file, log, and run directories.
Use the same Nix-pinned ClickHouse binary, user settings, table schema, and local
MergeTree configuration as the single-node experiments.

Test 1-, 2-, and 4-shard topologies sequentially. Each topology stores one total
copy of the selected source corpus divided by:

[source,text]
----
cityHash64(tenant_id, dataset, event_id) % shard_count
----

The exact production hash remains a schema decision; the experiment requires
only one recorded stable expression for all compared topologies.

Do not add replicas initially. Sharding/fanout and replication/recovery are
different questions and should not be confounded in the first simulation.

== Why native multi-instance processes

Separate server processes exercise actual ClickHouse network protocol,
`Distributed` query planning, leaf-local partial aggregation, coordinator
merging, timeout, and unavailable-shard behavior. Multiple databases or tables
inside one server would not reproduce those boundaries. Containers add image,
overlay, mount, and ownership differences without making the shared hardware a
real cluster, so the first harness should extend the existing native benchmark
server pattern.

Each leaf will receive explicit CPU affinity and memory limits where the host
supports them. All leaves still share one CPU socket, memory subsystem, ZFS ARC,
and striped SSD pool; those limitations must remain visible in every result.

== Dataset profiles

Start with one natural approximately 1 TB logical day using the sort key
selected by Experiment 013. One distributed physical copy should require about
the same total bytes as the existing one-day table, regardless of shard count.

The natural corpus contains one benchmark tenant and dataset, which represents
an elephant tenant spread across all shards by event identity. Add a
deterministic synthetic tenant mapping in a separate load to model:

- one dominant tenant plus several medium tenants;
- many small tenants;
- a highly skewed tenant/dataset distribution; and
- a small tenant whose ordinary query still fans out to every shard.

The mapping must preserve event values and identity checksums within each
logical tenant assignment and remain reproducible from source event identity.

== Query workloads

For every topology, run matching single-node and `Distributed` queries over:

. latest-event retrieval over narrow and full-day ranges;
. raw time-range counts and rates;
. selective and prevalent configured attribute predicates;
. dashboard count, heatmap, and percentile aggregate states;
. bounded raw-event retrieval from an attribute index;
. one large tenant and one small tenant; and
. serial, dashboard-concurrent, raw-concurrent, and mixed workloads.

The coordinator must receive aggregate states or bounded event rows, not all
matching raw rows. Record normalized SQL, result hashes or approximation
anchors, participating shards, leaf and coordinator query IDs, and execution
settings.

== Measurements

- End-to-end p50 and p95 latency and throughput by topology and workload.
- Coordinator queue, CPU, peak memory, result rows, and network bytes.
- Per-leaf rows, bytes, marks, CPU, memory, and query duration.
- Insert acknowledgement latency, throughput, pending distributed sends, and
  per-shard row/byte skew.
- Fixed fanout cost for small tenants and narrow time ranges.
- Local partial-aggregation reduction ratio before coordinator merge.
- Result correctness and expected-versus-participating shard coverage.
- Query cancellation and deadline propagation.

== Failure tests

Stop one leaf during controlled read-only queries and compare:

- complete execution with `skip_unavailable_shards = 0`, which must fail rather
  than return an apparently complete result;
- bounded-latency execution with `skip_unavailable_shards = 1`, where Lighthouse
  must report expected shards, participating shards, missing coverage, and a
  partial result; and
- cancellation or timeout while one leaf is slow.

ClickHouse does not by itself provide the full product-level coverage contract.
The experiment should identify the metadata the Lighthouse coordinator must add
instead of treating a successful partial response as complete.

== Interpretation limits

This mechanism is a distributed-systems simulation, not a scale-out capacity
measurement:

- loopback networking understates real network latency and failure modes;
- shared disks, ARC, memory bandwidth, and CPUs create contention that separate
  machines would not share;
- adding local shards may reduce performance even when real independent nodes
  would add capacity; and
- it cannot validate rack/AZ placement, replica reconstruction, or 100 TB
  recovery behavior.

It can still validate query semantics, sharding correctness, fanout overhead,
coordinator scaling trends, skew, observability, cancellation, and unavailable-
shard behavior before paying for a real cluster.

== Guardrails

- Run after Experiment 013 and remove its disposable sort-key candidate tables
  before loading distributed copies.
- Preserve the ten-day hot events, exact payloads, and immutable run artifacts.
- Run topologies sequentially and retain only one disposable distributed corpus
  at a time.
- Preserve at least 100 GiB free on the SSD dataset.
- Use high unprivileged ports and isolated directories; never reuse production
  service ports or data paths.
- Stop all coordinator and leaf processes on normal or failed harness exit.

=== CPU utilization interpretation

Leaf query-log CPU counters do not show sustained CPU saturation. The one-shard
topology allowed eight query threads and the two-shard topology allowed five per
leaf, ten total. Median summed leaf CPU seconds per wall second for full-day
queries were only 1.28-1.83 on one shard and 1.65-3.50 on two shards. The
coordinator used less than 0.01 CPU seconds per wall second for the measured
full-day heatmap, so coordinator CPU was not the limiting resource.

For the representative two-shard warm full-day heatmap, each leaf ran for
approximately 124-129 seconds, consumed 187-191 CPU seconds, and spent a summed
33 seconds in ClickHouse's disk-read timing while reading approximately 57 GB
through file descriptors. Together the leaves averaged 2.96 CPU cores during
the 127.84-second coordinator wall time, well below their ten-thread ceiling.
The speedup came from increasing useful parallel work, not from relieving a
previously saturated CPU.

The dynamic Map filter's warm regression also does not correlate with CPU
saturation. Two shards averaged 2.26 CPU seconds per wall second versus 1.54 on
one shard, but selected 36,794 marks versus 26,364 and read more data due to the
different uncompacted part layouts. Part layout and shared storage/cache effects
therefore confound that comparison.

These are per-query ClickHouse counters, not a host-wide sampled CPU trace. They
can establish that the queries did not sustain their available query-thread
capacity, but cannot exclude brief core saturation, frequency throttling, ZFS
work outside ClickHouse's query CPU counter, or contention from another host
process. The four-shard phase below adds host-level CPU, iowait, frequency, and
per-device counters; the cloud experiment must retain equivalent evidence.

The result separates useful parallelism from fixed fanout cost. Two local
leaves reduced most scan-and-aggregate warm latencies by 35-39%, despite sharing
one machine. Recent-tail queries gained little or regressed because the
coordinator must contact and merge both leaves. The full-day dynamic Map filter
did not improve reliably and every raw full-day distribution remains far above
the interactive target. Standard distributed partial aggregation works, but it
does not replace the tenant attribute index and materialized aggregate states
validated by Experiments 008 and 012.

`/mnt/fast-storage/lighthouse/runs/experiment-014-distributed-query-v1-{1,2,4}s`.

CPU averaged 55.6% busy (75.4% p95) and iowait averaged 0.9% (2.9% p95). The

75.0% p95, and a queue depth of 1.34. The QVO was therefore near saturation
during high-load intervals, but neither CPU nor both striped devices were
sustained at saturation over the run. Unequal device behavior is a material
limit of this local stripe.

=== Deferred profiles

The initial plan also proposed synthetic tenant distributions, concurrent raw
and dashboard workloads, and cancellation while a leaf is deliberately slow.
Those profiles were not executed in this run. The natural corpus has one tenant,
and the four-process load already approached the shared host's CPU and QVO
limits; adding synthetic copies or concurrency would primarily measure this
machine's contention rather than independent-node scaling. The smoke matrix did
validate complete failure versus explicit partial results with a leaf down, but
not slow-leaf deadline propagation. These items remain explicit cloud-test or
focused follow-up requirements rather than implied completed evidence.

=== Current conclusion

The measured path supports the proposed initial architecture:

* Standard ClickHouse `Distributed` fanout preserved exact results and correctly
  merged aggregate states at one, two, and four shards.
* `cityHash64(tenant_id, dataset, event_id)` placed the elephant tenant evenly
  without a virtual-partition metadata layer.
* Fixed fanout is visible for small tail queries, but remains sub-second at four
  local shards.
* Raw dynamic-field scans do not scale acceptably; configured shared attribute
  indexes are required.
* Materialized count, histogram, and t-digest states keep dashboard queries near
  100 ms with negligible storage compared with raw events.
* Lighthouse still needs expected-versus-participating shard metadata because
  ClickHouse partial results do not disclose product-level coverage.

This local experiment establishes semantics and relative fanout behavior, not
production capacity. Synthetic multi-tenant concurrency, cancellation under a
slow leaf, replicas, network latency, and independent-node throughput remain for
the cloud experiment or focused follow-up runs. The current evidence does not
justify implementing virtual partitions or a custom distributed query layer
before standard ClickHouse deployment is measured on independent hosts.
