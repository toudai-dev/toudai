== Question

Which typed canonical storage approach should the RFD pursue?

. *(A) Payload plus serving Maps plus explicit type information.* Can the
   versioned post-policy typed canonical payload and the queryable type
   information be produced and inserted with stock Collector components, and
   what is the actual insertion mechanism?
. *(B) Minimal custom exporter/mapping path.* What can a component that owns the
   insert statement write, and what transport machinery can it reuse?
. Which serving representation satisfies the typed-value contract on the same
   fixture — a companion type `Map` or a tagged-value `Map` — and at what
   measured storage and execution cost?
. Is the stock `json: true` exporter mode a sufficient typed control, and does a
   preserved payload repair string-only Map query results?

This is a compatibility and semantic experiment, not an implementation of the
ingestion service, a custom Collector component, or a query planner. Payload
placement (hot column, Map-carried value, separate table, or object storage) is
treated as an open design variable; the experiment compares logical preservation
and consistency, and reports placement costs, without turning the harness DDL
into a product requirement.

== Hypothesis

Written before the fixture run, from the pinned component documentation and
source:

* The stock ClickHouse exporter inserts through fixed, explicit column lists
  (`logs_insert.sql` / `traces_insert.sql`, v0.161.0); it has no custom-column,
  expression, or mapping option, so any managed column the exporter does not
  name can only be a `DEFAULT`, `MATERIALIZED`, or `ALIAS` column.
* The stock `json: true` mode writes ClickHouse `JSON` columns through
  `json.Marshal(attributes.AsRaw())`, so it should preserve some type structure
  (string versus number, structured arrays/maps, `null` versus `''`) but cannot
  represent non-finite doubles at all, and integral `int64`/`float64` values
  should collide because Go marshals `float64(1)` as `1`.
* The stock expressions tested here cannot compute a companion type map or a
  typed canonical payload: OTTL has predicates (`IsInt`, `IsDouble`, ...) and
  `MapEach`, but the pinned function inventory has no conditional operator to
  produce a per-key type name and no typed JSON marshal, and the natural
  per-key expression does not parse. The closest expression, `stringify_all`,
  performs the same lossy `AsString` conversion the exporter already performs.
  Conditional `where` statements across multiple transform passes, other
  processors, and components outside the pinned distribution were not
  evaluated, so this is a claim about the tested expressions and the pinned
  function inventory, not proof that no stock configuration can produce type
  information.
* Both a companion type `Map` and a tagged-value `Map` can carry the required
  typed semantics if the mapping step is correct; the tagged encoding should
  cost more bytes and more group-by work, and the query layer must enforce the
  contract rules over whichever representation is chosen.
* Preserving the payload does not change what a string `Map` returns for a
  filter or group; typed results require the type information.

Two hypotheses were incomplete and were corrected by the run: ClickHouse fills
omitted managed columns with the type default instead of rejecting the insert
(so a plain payload column is silently empty rather than an error), and
`json: true` preserves `int` versus `string` but still collapses `int 1` and
`double 1.0` into `Int64 1`.

== Fixture

A deterministic synthetic corpus built by `019/harness/fixture.py`. All events
share fixed timestamps (`2026-09-01T07:00:00.123456789Z`) and a fixed typed
inventory chosen where string coercion changes meaning: integer 1, double 1.0,
and string `"1"`; integers above 2^53 and `Int64` limits; non-finite doubles and
negative zero; bytes; arrays and maps; explicit empty, empty string, and missing
keys; duplicate keys; case variants; resource/scope/record namespace collisions;
span scope attributes on a separate instrumentation scope; and a malformed
(negative) span duration. It adds rows needed for representation comparison: one
row per type for the same key, numeric-ordering rows, and aggregate/overflow
rows. Expected results are computed from this typed inventory, not from
ClickHouse output.

== Method

Seven phases run in one process (`019/harness/run.sh all`), each starting and
stopping its own services and asserting against independent expectations:

. *stock-map*: stock OTLP to the stock Map exporter (`create_schema: true`); the
  exact serving strings and the duplicate/scope/duration behavior are captured.
. *stock-json*: stock `json: true` mode. The full fixture (with NaN) is emitted
  first as negative evidence, then the reduced `typed-safe` fixture is emitted to
  characterize the remaining typed cases.
. *managed*: `create_schema: false` against a Lighthouse-managed table that adds
  a `DEFAULT` column, `MATERIALIZED` projections, and a plain payload column with
  no default; the exporter's actual `INSERT` statement is captured from
  `system.query_log`.
. *transform*: a config attempt at a per-key type map, and `stringify_all` as the
  closest stock expression.
. *identity*: a credential-selected pipeline injects the trusted workspace
  attribute before any mapping step; the stored row must carry the trusted value.
. *semantics*: the mapping prototype loads every candidate representation and
  the checks compare them with expectations computed from the fixture inventory.
. *cost*: a deterministic 50,000-row typed corpus is loaded into each
  representation, parts are merged with `OPTIMIZE ... FINAL`, and storage and
  warm query costs are measured.

The mapping prototype in `019/harness/represent.py` and `019/harness/model.py` is
harness code: it is what a custom processor or exporter would have to do, not a
Collector component. The `prototype.*` checks implement contract rules (reject
unsupported operations, reject integer overflow) in the harness; they are not
ClickHouse guarantees.

A post-run evidence review added the stock-exporter oracle checks and the
literal group-by expectations, scoped the stock-processor claim to the tested
expressions and the pinned function inventory, and separated the
representation-level results from the harness-enforced prototype rules. The
committed evidence is the reviewed run.

=== Expectation independence

Which side produces each expected value matters, so the harness keeps them
separate:

* *Oracle (typed inventory):* `fixture.EVENTS` / `fixture.SPAN_EVENTS` in
  `019/harness/fixture.py`. `verify.py:metric_rows`, `expected_type_counts`,
  `expected_metric_groups`, `expected_int_order`, `expected_lexical_order`, and
  `expected_stock_string_count` compute expectations from that inventory, not
  from ClickHouse output.
* *Representations under test:* `019/harness/represent.py` and
  `019/harness/model.py` (`stock_string`, `namespace_maps`, `tagged_namespace`,
  `canonical_payload`).
* *Independent decode:* `verify.py:decode_canonical` is a separate decoder from
  `model.py:canonical_node`, so the lossless round-trip check does not share
  encoder code.
* *Independent conversion oracle:* `verify.py:phase_stock_oracle` compares both
  the decoded canonical values (through `model.stock_string`) and the
  representation's serving Maps with the rows the pinned Collector actually
  wrote into `stock_map.otel_logs`. That is the discriminating check for the
  conversion helper; without it, expectations derived from the same helper would
  be circular.
* *Literal expectations:* the 28 `stock_map.*` checks and the new
  `semantics.*.group_by_literals` checks pin literal values and counts authored
  from the inventory (for example int `1` in three rows, `NaN`, empty string,
  explicit empty, bytes base64, and bool false), so they do not depend on the
  Python conversion helper either.

=== Stock `json: true` as a bounded semantic control

Experiment 006 rejected native `JSON` at 1 TB scale (file-descriptor, part-count,
inode, and free-space failures at 63.2% of one day, projecting 19.6% larger than
`Map`), and this experiment does not reopen the Map serving baseline; `json:
true` is measured only as a small semantic control. Measured on the fixture:

[options="header",cols="2,2,2"]
|===
|Received value |Stored in `JSON` mode |Meaning change

|int 1 |`Int64 1` |none, type kept
|double 1.0 |`Int64 1` |*collides with int 1* (`json.Marshal` writes `1`)
|string "1" |`String "1"` |distinct from numbers
|int 9007199254740993 |`Int64 9007199254740993` |exact
|int64 min |`Int64 -9223372036854775808` |exact
|bool false |`Bool false` |distinct from `Int64 0`
|explicit empty |`NULL`, key present in `*Keys` |distinct from `''`
|bytes `00 01 fe ff` |`String "AAH+/w=="` |type lost, same as Map mode
|array / map |structured JSON |no collision with JSON-like producer strings
|double NaN / Inf |*export fails* |`json: unsupported value: NaN`; the request is retried and dropped (28 records)
|duplicate keys |last value wins |the stock Map keeps both copies
|span scope attributes |dropped |no `ScopeAttributes` column
|negative span duration |`UInt64` underflow |same as Map mode
|===

Type-strict comparison is native in this mode: `int.one = str.one` raises
`NO_COMMON_TYPE` instead of coercing (measured), while `int.one = double.one`
returns true because both are stored as `Int64`.

=== Stock processor gap

The natural OTTL expression for a companion type map fails to load:

[source,text]
----
Error: invalid configuration: processors::transform/types: statement has invalid syntax: 1:76: lexer: invalid input text "? \"int\" : \"other..."
----

`stringify_all(attributes)` loads and produces the same conversion the exporter
already performs: `int.one`, `double.one`, and `str.one` all arrive downstream as
`stringValue: "1"`. Within the tested configuration, neither expression produces
the type information: the natural per-key type expression fails to load, and
`stringify_all` is lossy. Source inspection of the pinned OTTL function inventory
finds no conditional operator and no typed marshal, so no expression of the
tested form can build the map. This experiment did not evaluate conditional
`where` statements across multiple transform passes, other processors, or
components outside the pinned distribution; if no tested stock configuration
produces the type information, both approaches need a mapping component outside
that configuration, and the choice is where that component sits.

Rows that name the prototype are harness-enforced contract rules: the
representation makes them possible, but ClickHouse does not enforce them. The
Interpretation separates the representation-level results from the
query/mapping-layer obligations.

Key measured details:

* The companion-type serving values are byte-identical to the stock Map values
  (`1`, `1`, `1` for int/double/string); only the type map is added. This means a
  stock exporter path can keep writing the same Map values while a mapping
  component adds type information.
* Preserving the payload does not repair Map semantics: with the payload column
  present, `record['metric.value'] = '1'` still returns 5 rows, while extracting
  the payload returns the correct 3 int rows — at extraction cost.
* A preserved payload is not the only requirement: the type information must be
  produced before stringification, and the tested stock expressions do not
  produce it.

* On this corpus, payload bytes dominate every variant, so placement (hot
  column, separate table, or object storage) matters more than the serving
  encoding for total bytes. This experiment does not select a placement, and
  Experiment 009's separate normalized-events and exact-payload design remains
  the current evidence; the corpus is not a retained-scale measurement.

=== Identity ordering

The credential-selected pipeline (`routing` connector plus a `resource`
processor, the stock mechanism validated in Experiment 018) stores the trusted
workspace attribute even when the producer sends a forged one: the stored value
is the trusted workspace and no row carries the forged value. A canonicalization
step must therefore be ordered after the trusted-scope processor; this experiment
does not test dynamic credential resolution, key rotation, or cross-workspace
batching.

== Interpretation

*Supported by the measurements.*

* The stock ClickHouse exporter cannot insert a canonical payload column: its
  `INSERT` names a fixed column list, any other column receives its
  `DEFAULT`/type default, and no configuration can supply it. A `MATERIALIZED`
  projection can promote a Map-carried value into a queryable column, and a
  Map-carried type JSON can be parsed into a companion type `Map`.
* No stock processor configuration tested here produces the typed canonical
  payload or the type information: the natural per-key expression fails to load
  and `stringify_all` is lossy, and the pinned OTTL function inventory has no
  per-key conditional type name and no typed marshal. Conditional `where`
  statements across multiple passes, other processors, and components outside
  the pinned distribution were not evaluated, so this is not proof that no stock
  configuration can produce the type information.
* Both required serving encodings support the representation-level semantics
  the contract requires, verified by SQL over the stored representation against
  expectations computed from the typed inventory: type-sensitive equality
  filters and group keys, numeric rather than lexical ordering, missing versus
  explicit empty versus empty string, false versus zero, exact `Int64` values
  above 2^53 and at the signed limits, non-finite and bytes/nested carriage with
  their types, a lossless canonical round-trip, and serving values that equal
  both the decoded canonical values and the rows the pinned stock exporter
  actually stored. The companion type `Map` costs less and keeps stock serving
  values; the tagged-value `Map` needs no extra column but costs more bytes and
  more group-by work.
* The remaining contract guarantees are *query/mapping-layer obligations* that
  the representation can only make possible. This experiment enforced them in
  the harness query prototype, not in ClickHouse, so they are not established
  for the product: explicit errors for comparisons and aggregations on bytes,
  arrays, maps, and non-finite doubles; exclusion of non-matching types before
  aggregation (or an error); integer aggregates accumulated without wrap and
  rejected on overflow; and contributing-value counts separate from event
  counts. A production query layer must implement those rules, and a production
  mapping layer must produce the type information they depend on.
* `json: true` is not a sufficient typed control: it preserves string versus
  number and structured collections, but drops the request on NaN, collides
  integral int/double values, loses the bytes type, collapses duplicate keys, and
  still cannot store span scope attributes. It stays a bounded control, and
  Experiment 006's scale rejection is unchanged.
* A preserved payload does not repair string-only query results; typed answers
  require the type information (or payload extraction, measured at much higher
  read cost).
* A dedicated payload column written directly (the B-style mapping spike) stores
  the payload once; the stock-compatible Map-carried variant stores it twice.
  This is a mapping and schema spike: it does not establish producer-visible
  per-record rejection or validation timing, because an exporter sits behind
  receiver and exporter queues where OTLP success is already queue admission
  (Experiment 018).

*Not supported by the tested components or not established here.*

* That a custom exporter can keep the typed contract *and* the stock exporter's
  batching, retry, queue, and failover behavior. This experiment did not build or
  run a custom component; it only shows the mapping/schema it could write, and
  that `exporterhelper` is the source-documented reuse point
  (`clickhouseexporter/factory.go` in the pinned source), not a verified
  integration.
* That a custom exporter would give producers per-record rejection or a
  particular validation timing. Validation inside an exporter sits behind
  receiver and exporter queues, where OTLP success is already queue admission
  (Experiment 018); partial success, per-record error reporting, and where
  validation would have to live to change producer-visible behavior were not
  tested.
* That `json: true` is viable at retained scale (Experiment 006 already rejected
  native JSON at 1 TB; nothing here reopens that).
* That multi-destination fan-out (serving plus canonical) is atomic or free of
  partial delivery. A `routing` connector fan-out to a second exporter was not
  exercised; acknowledgement and partial-failure semantics for that topology
  remain untested.
* Dataset routing, workspace-scoped validation/redaction before canonicalization,
  dynamic credential resolution, and reconstruction of a serving layout from the
  canonical payload. Only a static credential-to-workspace binding and its
  ordering before the mapping step were tested.
* Capacity, throughput, or retained-volume behavior: the cost corpus is 50k rows
  on loopback.

*Unknown after this experiment.*

* Whether a custom processor (payload/type attributes plus the stock exporter) or
  a custom exporter (own insert) is the smaller long-term component; both need
  the same mapping semantics, and the experiment deliberately leaves that choice
  open.
* How the canonical payload should be placed physically (hot column, separate
  table, or object storage) and how that interacts with retention, backup, and
  reconstruction; the experiment measured the column and Map-carried variants
  only.
* Whether the query planner can use the companion type `Map` and the payload
  together without reading the payload for normal filters.

== Limitations

* The environment is a two-vCPU sandbox; no throughput, latency, or capacity
  claim follows. Cost numbers are a 50k-row micro-measurement after
  `OPTIMIZE ... FINAL`, not a benchmark.
* The mapping prototype is harness code, not a Collector component. It proves the
  representation semantics and the shape of the required insert, not that a
  production component implements them.
* `prototype.*` rejection behavior is harness-side contract enforcement, not a
  native ClickHouse guarantee.
* The identity phase reuses Experiment 018's static credential routing; dynamic
  identity, key rotation, and cross-workspace batching were not exercised.
* The stock-processor claim covers the two expressions in
  `collector-transform-types.yaml` and `collector-transform-stringify.yaml` plus
  the pinned OTTL function inventory. Conditional `where` statements across
  multiple transform passes, other processors, and components outside the pinned
  distribution were not evaluated, so the claim is not that no stock
  configuration can produce type information.
* Expectations for the representation checks come from the typed inventory; the
  conversion helper itself is validated against the pinned exporter's stored
  values in `verify.py:phase_stock_oracle` and by literal checks. The tagged-value
  encoding is checked with literal encoding expectations
  (`semantics.tagged.value_encoding_roundtrip`) and the shared inventory and
  literal expectations, not against the exporter's stored values, because the
  stock exporter has no tagged mode.
* The payload encoding in the harness is one versioned JSON representation with
  explicit type tags; it is not proposed as the final wire format.
* `json: true` measurements cover the fixture only, and its scale behavior is
  governed by Experiment 006's rejection.
* Expectations are pinned to the pinned versions; a component upgrade is expected
  to change some characterizations, which is the point of the checks.

== Follow-ups

* Before building a custom component, test whether conditional `where`
  statements across multiple transform passes or another stock processor can
  produce the companion type map; this experiment did not rule that out.
* Choose the mapping component boundary (processor plus stock exporter, or a
  minimal exporter) and implement the typed canonical payload and companion type
  `Map` mapping; re-run this fixture and Experiment 018's acknowledgement/failover
  phases against the chosen component.
* Decide canonical payload placement with the retention, backup, and
  reconstruction plan, and measure the chosen path at retained scale; keep
  Experiment 009's split as the current evidence.
* Define the query-layer type rules from the contract (strict equality, group
  keys including type, numeric ordering, aggregate type errors and overflow
  rejection, unsupported-operation errors) and table-test them against this
