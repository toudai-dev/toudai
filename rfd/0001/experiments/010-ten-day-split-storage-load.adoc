== Question

Can one ClickHouse node retain approximately ten logical terabytes of natural
events by keeping normalized Map events on striped SSD and exact raw payloads
on bulk ZFS, while maintaining resumable ingestion and sufficient SSD headroom
for tenant acceleration?

== Environment

The benchmark-only `fast-storage` pool was recreated, with explicit approval,
from a two-disk mirror as a two-vdev stripe:

- Samsung 870 QVO 1 TB
- Samsung 870 EVO 1 TB
- ZFS usable size: 1.81 TiB
- Compression: off
- Record size: 128 KiB
- `atime`: off
- Autotrim: on
- Redundancy: none; either SSD failure loses the benchmark pool

All prior experiment evidence was copied to
`storage/lighthouse-bench/preserved-before-stripe-2026-08-19` and 1,115 regular
files were checksum-verified before pool destruction.

== Method

Load the first ten natural day directories from `/mnt/storage/lighthouse`.
Only one day is staged at a time in `gcp_source` on bulk storage. Each staged day
is transformed in hourly windows into:

- normalized `events_map_hot` on striped SSD; and
- exact `event_payloads` on bulk ZFS.

The loader records file, window, row, query-log, storage, and free-space
evidence and is resumable at file and hourly target boundaries. It truncates
the decoded source stage after both targets for a day are complete.

the exact payload table.

The normalized hot table occupies 9.94% of calibrated logical input, or 10.06×
logical-to-physical compression. Exact payload occupies 7.04%, or 14.21×
compression. Together they occupy 16.98% of logical input for a 5.89× effective
ratio. The split representation is 1.64× the already compressed source Parquet
size because it retains both normalized query-serving fields and independently
addressable exact payloads.

At final evidence capture, the hot ZFS dataset was 57% used with 785 GiB
available, and the bulk benchmark dataset was 28% used with 2.42 TiB available.
Both pools were online with no read, write, checksum, or known data errors. The
single node therefore retained the target corpus while preserving substantial
SSD headroom for the next acceleration experiment.

=== Recovery evidence

The run has preserved validated boundaries through three interruptions:

. After Day 1, ClickHouse's large-table safety limit rejected staging-table
   truncation. The loader now supplies the explicit size override and resumed
   without reloading the validated targets.
. After Day 5, staging-table truncation completed server-side but the original
   loader did not preserve the client exit reason. The loader now records its
   phase, command, line, exit code, and combined output on failure.
. During Day 8, replacement of the benchmark executor killed ClickHouse and the
   loader without allowing the shell failure trap to run. Sixteen hot windows
   and fifteen payload windows had durable validation markers. The interrupted
   payload insert contained 2,468,087 unvalidated rows; they were removed with
   a bounded lightweight delete before replay.

The third recovery exposed two loader defects. Additional July source data had
changed the first ten lexically sorted directories, so resume initially failed
its immutable configuration check. Resume now reads the persisted day list from
the run configuration. A subsequent attempt incorrectly treated the active Day
8 staging table as leaked data from an earlier completed day and truncated only
that rebuildable staging copy. Completed days now skip cleanup, and the first
incomplete day distinguishes missing active staging from a previous day's
untruncated stage using its file markers.

Day 8 was restaged, its preserved windows were rechecked, and loading continued
through Day 10 without another correctness failure. The original process used
ClickHouse 26.3.15.4; recovery after the executor replacement used the
Nix-updated 26.3.17.110. Query and throughput comparisons must therefore
identify the patch-version boundary.

The six-day wall duration is not a sustained-ingestion result. It includes
operator pauses, executor replacement, staging reconstruction, failure
diagnosis, a ClickHouse patch change, and concurrent external writes to the bulk
pool. Per-window query-log data remains useful, but production ingestion capacity
requires a separate controlled measurement.

== Interpretation

The split physical design passes the retained-capacity and full-resolution
correctness gate on this host. Approximately 10.81 TB of calibrated logical
input fits in 1.67 TiB of active ClickHouse parts while preserving every accepted
normalized event and exact source payload. Moving payloads off SSD avoids making
normal exploration pay their 708 GiB footprint.

This experiment does not establish interactive query latency, acceleration
maintenance cost, workload concurrency, or production ingestion throughput.
Those are the next gates. It also does not prove object storage or durable replay:
the bulk payload table is a useful physical boundary, not the final archive
contract.
