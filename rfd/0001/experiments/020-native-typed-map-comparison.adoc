== Question

Experiment 019 compared a companion type `Map` with a tagged-value `Map` but never
evaluated separate native typed Maps. This experiment asks:

. Can a native typed layout (`Map(String, Int64)`, `Map(String, Float64)`,
   `Map(String, String)`, `Map(String, Bool)`) serve the typed-value contract on
   the same typed fixture, and what presence/type bookkeeping does it need?
. Can the full per-key companion type `Map` be avoided, or does dropping it
   break missing/present or canonical type identity for bytes, arrays, maps, and
   non-finite doubles?
. What do the alternatives cost in compressed storage, warm query reads, and
   mapping/insert work, measured on the same data with the same sort key, codec,
   and part state?
. Which rules remain query-layer or mapping-layer obligations that ClickHouse
   does not enforce?

This is a storage/mapping/query spike: it does not implement a Collector
component, an ingestion service, or a query planner, and it does not select
production DDL.

== Hypothesis

Written before the run:

* `Map(String, Int64)`, `Map(String, Float64)`, `Map(String, String)`, and
  `Map(String, Bool)` are supported on the pinned version; a missing key lookup
  returns the type default, so every typed query needs a presence or type guard.
* Native typed value Maps should reduce the serving value bytes for
  numeric-heavy data, but small integers stored as binary `Int64` may compress
  worse than short decimal strings; the result is corpus-dependent.
* A full per-key type sidecar costs about the same as Experiment 019's companion
  type `Map` (same shape and logical content), so a full-sidecar native layout
  saves only the value-map delta. A minimal key-only map for canonical-only
  types plus explicit empty should cost almost nothing on realistic data.
* Known-type queries can guard directly on the matching typed value Map
  (`mapContains(record_int, k) AND record_int[k] = v`), so the minimal layout
  need not scan five Maps for a filter, ordering, or sum whose type is known.
  Only presence and grouping for a key whose type is unknown in advance require
  the union/type expression.
* Non-finite doubles are storable in `Float64`; presence/type inspection of them
  is supported, and only value comparison/aggregation is a query-layer rule.
* Native numeric columns do not make `sum(Int64)` safe; it still wraps.
* Bytes, arrays, and maps can stay canonical-only with an explicitly unsupported
  comparison/aggregation surface, while their presence/type identity is
  preserved by bookkeeping.

One hypothesis was corrected by the run: a minimal layout does *not* need to
collapse the canonical-only types. A small `other` map keyed by the
canonical-only keys keeps bytes, array, map, and empty distinct, so the minimal
layout preserves full type identity rather than trading it away.

== Method

Five phases run in one process (`run.sh all`), each starting and stopping its own
ClickHouse server and asserting against independent expectations:

. *capabilities*: probes the pinned version for the types and behaviors the
   layouts depend on (Map value types, `LowCardinality` keys, `Nullable` values,
   `Int128`, duplicate keys, missing-key defaults, non-finite doubles,
   `sum(Int64)`).
. *semantics*: loads the typed inventory into every candidate and checks typed
   equality, grouping, ordering, presence, canonical-only types, aggregates,
   namespace separation, canonical round-trip, and serving equivalence.
. *negative*: loads deliberately wrong layouts and shows the assertions are
   discriminating; `test-run-failure-modes.sh` additionally runs the check set
   against the wrong table and asserts a nonzero exit.
. *cost*: loads both 50,000-row corpora into per-corpus databases, merges each
   table to one part (`OPTIMIZE ... FINAL`), and measures compressed storage,
   warm query reads, and mapping/insert work.
. *files*: asserts the imported-source hashes and that the evidence files exist.

=== Pinned-version capabilities (characterization)

Measured on ClickHouse 26.8.2.7-lts:

* `Map(String, Int64)`, `Map(String, Float64)`, `Map(String, String)`,
  `Map(String, Bool)`, `Map(String, UInt8)`, `Map(String, Int128)`,
  `Map(LowCardinality(String), ...)`, and `Map(String, Nullable(Float64))` all
  create, insert, and read.
* A `LowCardinality(String)` value type inside a `Map` is kept in the declared
  column type (`system.columns.type` and `DESCRIBE` both report
  `Map(LowCardinality(String), LowCardinality(String))`), while a map lookup
  *expression* reports `String` (`toTypeName(m['a'])`), i.e. the dictionary
  encoding is not part of the single-key expression result type. This
  experiment did not inspect the on-disk encoding directly, so it makes no claim
  about whether the dictionary survives serialization.
* A missing key lookup returns the type default: `0` for Int64/Float64, `''`
  for String, `false` for Bool. `mapContains` is the presence test.
* A `Map` literal can hold duplicate keys (`length(mapKeys(map('a',1,'a',2)))`
  is `2`); lookup returns the first value. There is no native uniqueness
  constraint.
* `JSONEachRow` accepts `NaN`, `Infinity`, and `-Infinity` for `Float64` map
  values; `-0.0` is stored and printed as `-0`; negative zero survives the
  round-trip and equals `0`.
* `Float64` represents `Int64` minimum exactly:
  `toFloat64(-9223372036854775808) = -9223372036854775808` and the round-trip
  through `toInt64` is exact; `toString` prints `-9223372036854776000`, which is
  decimal formatting, not numerical loss. `9007199254740993` (2^53 + 1) is a
  genuine precision-loss control: it equals 2^53, not 2^53 + 1, in `Float64`.
* `sum(Int64)` wraps to `-1` over `[Int64 max, Int64 max, 1]`; `sum(Int128)`
  keeps `18446744073709551615`.
* A present `NULL` inside `Map(String, Nullable(Float64))` is distinguishable
  from a missing key by `mapContains`, which is an alternative explicit-empty
  representation this experiment did not select.

=== Query-layer and mapping-layer obligations (not ClickHouse guarantees)

* The harness prototype rejects value comparison and aggregation on bytes,
  arrays, maps, and non-finite doubles (7 prototype checks), while presence and
  type inspection of those values is supported and checked. Whether a
  presence/type predicate is in scope for canonical-only types is not enumerated
  explicitly by the contract; this experiment answers them in both native
  layouts, and notes that the stricter reading would only remove the
  canonical-only keys from the bookkeeping map (their presence would then be
  unavailable without reading the payload).
* Grouping or ordering *on* a non-finite double is not enumerated by the
  contract; the harness rejects comparison but does not exercise NaN grouping,
  and this experiment records that as unspecified rather than as conformance or
  rejection.
* Integer aggregates must be type-filtered and range-checked by the query layer:
  the fixture's integer total is 9,232,379,236,109,516,923, above `Int64`, so a
  plain `sum(Int64)` over the typed column wraps to -9,214,364,837,600,034,693.
  `sum(Int128)` keeps the true total.
* Duplicate keys inside one collection and one-typed-map-per-key are enforced by
  the mapping prototype only. ClickHouse has no unique-key constraint, and
  producer-visible rejection timing behind Collector queues was not tested.

=== Tradeoffs beyond byte totals

* *Absent-key handling.* Every native query needs an explicit presence or type
  guard because a missing lookup returns the type default. Known-type queries
  use one guard on the matching value Map; unknown-type presence and grouping
  use the sidecar (one `mapContains`) or the minimal layout's five-map union.
  The guard is also what keeps aggregates from silently including defaults: an
  unguarded `sum(record_int[...])` includes every non-int row as zero.
* *Mixed-type grouping.* A group key that includes type is natural in the
  sidecar layouts (`record_types[k]`) and needs a five-way `multiIf` plus a
  union presence predicate in the minimal layout. The type-change fixture
  (`attr.mixed` as int and string across rows; int/double/string `1` rows)
  groups correctly in all three, but the minimal expression is more complex and
  its measured CPU time is higher.
* *Extra map scans.* Only unknown-type presence and grouping scan five Maps in
  the minimal layout. Compressed bytes were not uniformly higher in the
  measurement because the `OR`/`multiIf` expressions short-circuit, but CPU time
  was higher and the expression is harder to generate than a single sidecar
  lookup.
* *Insert and schema complexity.* Native layouts need four value Map columns per
  namespace instead of one, plus bookkeeping; the schema is wider and the
  mapping step must validate that each key lands in exactly one map. The
  minimal layout needs one extra small map and the same validation. ClickHouse
  enforces none of this.
* *Namespace asymmetry.* Splitting small, type-diverse namespaces (resource,
  scope) into typed maps costs more than a single string map; the typed layout
  pays off in the wide record namespace. A production design could keep typed
  maps for the record namespace only, which this experiment did not measure as a
  separate variant.

== Interpretation

*Supported by the measurements.*

* A native typed layout serves the typed-value contract on the same fixture:
  type-sensitive filters and group keys, numeric ordering, missing versus
  present versus explicit empty versus empty string, `false` versus `0`, exact
  `Int64` values including the limits and above 2^53, non-finite doubles and
  negative zero, namespace separation including span scope attributes, and a
  lossless canonical round-trip with serving Maps that equal the decoded
  canonical values and types.
* The full per-key companion type `Map` can be avoided without weakening the
  contract: a key-only `other` map for the canonical-only types (bytes, array,
  map) and explicit empty preserves missing/present and full type identity for
  the retained values, including non-finite doubles, which live in the `Float64`
  value map and are only restricted for comparison and aggregation.
* On the reused 019 corpus and the realistic variation, native typed Maps reduce
  compressed storage versus the companion baseline: 8.7-8.9% (`base`) and
  4.9-11.2% (`diverse`) of the total including payload, or 21.0-25.9%
  (excluding payload) when the minimal layout is used. The full sidecar holds
  the same logical content as the companion type map and costs about the same
  physical bytes.
* Known-type query reads also favor the native typed layouts on this corpus:
  a typed equality filter with a direct typed-map guard read 355,229 bytes
  (`native minimal`) and 355,237 bytes (`native typed`) versus 1,339,039 bytes
  (`companion`) on `base`, and 229,854 / 229,854 / 1,047,661 on `diverse`,
  because the companion layout must read its whole string value Map.
* The minimal layout's cost is confined to unknown-type presence and grouping,
  where it must union five Maps: compressed bytes were not uniformly worse in
  the measurement, but CPU time was higher (for example `diverse` presence
  11,649 vs 5,042 microseconds), and the expression is harder to generate. The
  earlier 2-3.9x read-amplification figure was a query-generation artifact (a
  blanket union/type expression for known-type operations) combined with the
  quantized `read_bytes` metric; it is not a layout requirement.
* Native numeric columns do not make integer aggregation safe: `sum(Int64)`
  wraps (measured on both the capability probe and the fixture, whose total
  exceeds `Int64`), while `sum(Int128)` keeps the true total. Type filtering,
  overflow rejection, and contributing-value counts remain query-layer work.
* Where the evidence favors each layout on this corpus: native typed Maps for
  record-namespace storage and for known-type query reads; the companion
  string `Map` for the small, type-diverse resource and scope namespaces and
  for a simpler schema and query generation; a sidecar (or the minimal layout's
  union) for unknown-type presence and grouping, where the sidecar is cheaper in
  CPU. Nothing here is retained-scale evidence: the older retained-scale
  benchmarks (Experiments 006, 010, and 011) validated string `Map` serving,
  not companion-type or native typed metadata, and no retained-scale evidence
  exists for either typed encoding.
* A collapsed Float64 layout and a two-map key both produce wrong answers that
  the check set rejects (nonzero exit) while the correct layout passes the same
  checks, so the assertions are discriminating rather than happy-path only.

*Not supported by the measurements or not established here.*

* That a production query planner can generate the minimal layout's union
  presence and `multiIf` type expressions efficiently, or that the measured
  read costs persist at retained scale. The corpus is 50,000 rows on loopback.
* That the companion type `Map` and the native typed Maps are equivalent for
  *other* query shapes (distinct counts, top-K, percentiles, nested traversal,
  ordering on non-finite doubles); this experiment covers the fixture's typed
  scalar surface plus explicit presence/type inspection.
* That any layout preserves the typed contract without a mapping component that
  enforces duplicate-key rejection and one-map-per-key consistency; ClickHouse
  has no uniqueness constraint.
* That a native typed layout is compatible with the stock Collector exporter
  path. This experiment does not build or run a custom component, and stock
  retry/queue/failover behavior for a mapping component remains unproven
  (Experiments 018 and 019 own that evidence).
* Capacity, throughput, or retained-volume behavior. The cost numbers are
  50,000-row single-part micro-measurements.
* That `LowCardinality(String)` dictionary encoding is lost inside a `Map`; the
  declared column type keeps it and only the lookup expression reports
  `String`. The on-disk encoding was not inspected.
* That native JSON is reconsidered: Experiment 006's rejection concerns native
  JSON at scale, and nothing here reopens it or applies to typed Maps.

*Unknown after this experiment.*

* Which native layout a production DDL should use, whether the PoC should keep
  the full sidecar, the minimal canonical-only map, or a mixed layout with typed
  maps only for the record namespace. No production DDL is selected here.
* How the canonical-only bookkeeping map behaves with high-cardinality bytes/
  array/map fields, and whether its presence is better served by the payload.
* Whether the query layer can use the typed Maps and the payload together
  without reading the payload for normal filters.
* Whether the minimal layout's unknown-type union cost is material at the
  retained volumes and query mixes the RFD targets.
* How payload placement (hot column, separate table, object storage) interacts
  with each serving layout; Experiment 009's split remains the current evidence.

== Limitations

* The environment is a two-vCPU sandbox; no throughput, latency, or capacity
  claim follows. Cost numbers are 50,000-row micro-measurements after
  `OPTIMIZE ... FINAL`, not benchmarks.
* Read costs use `ProfileEvents['ReadCompressedBytes']` with the query condition
  cache disabled and depend on the exact expression form (a direct typed-map
  guard versus a union/`multiIf`), which is why the report reports both forms
  and does not treat either as a layout property.
* The mapping prototype is harness code, not a Collector component. It proves
  the representation semantics and the shape of the required mapping, not that a
  production component implements them.
* `prototype.*` rejection behavior is harness-side contract enforcement, not a
  native ClickHouse guarantee.
* The cost corpora are synthetic. The `diverse` corpus is a bounded variation
  (bounded key population, deterministic sparsity, string-dominant types, one
  mixed-type key); it is not a natural workload and does not model
  high-cardinality identifiers or very wide events.
* Expectations are pinned to the pinned versions; a component upgrade is
  expected to change some characterizations, which is the point of the checks.
* The companion baseline is rebuilt with Experiment 019's encoding rather than
  re-measured through the stock Collector; Experiment 019 owns the
  stock-exporter oracle and its scale evidence.
* The minimal layout's type/presence expressions are hand-written SQL for the
  fixture; a production planner would generate different SQL.

== Follow-ups

* Decide the mapping component boundary (processor plus stock exporter, or a
  minimal exporter) and re-run this fixture against it; Experiments 018 and 019
  define the compatibility and acknowledgement work that remains.
* Decide whether the PoC DDL uses a full type sidecar, a minimal
  canonical-only map, or typed maps only for the record namespace, and record
  the choice with this experiment's storage and read-cost evidence.
* Table-test the query-layer type rules (strict equality, group keys including
  type, numeric ordering, aggregate type errors and overflow rejection,
  unsupported-operation errors) against this fixture before implementing the
  planner.
* Measure the minimal layout's known-type direct-guard path and its
  unknown-type union cost at retained scale before choosing it over a sidecar.
* Decide canonical payload placement with the retention, backup, and
  reconstruction plan; keep Experiment 009's split as the current evidence.
* If the query layer must answer presence/type for canonical-only keys without
  bookkeeping, define that as an explicit payload-read path rather than
  collapsing the values into strings.
