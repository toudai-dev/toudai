== Question

What volume, event-time coverage, schema shape, and approximate logical JSON
size does the available `~/storage/lighthouse` corpus represent?

== Environment

- Host: Linux x86-64, 12 logical CPUs, 62 GiB RAM
- Source storage: approximately 6 TiB available during profiling
- DuckDB: v1.5.2
- ClickHouse available for later tests: 26.3.15.4 LTS
- Source path: `/home/darwin/storage/lighthouse`

The corpus was previously retrieved from GCP Logging as JSON and compacted into
Parquet. It contains logs, not a representative trace or native-metrics corpus.

== Method

Parquet footer metadata supplied file sizes, row counts, row groups, and
timestamp bounds without decoding every event. A representative file was then
scanned to profile event width, field counts, cardinality, and canonical JSON
reconstruction size:

[source,text]
----
/home/darwin/storage/lighthouse/2026-08-01/compact-0000.parquet
----

Representative-value cardinalities use DuckDB's approximate distinct-count
function and should not be interpreted as exact counts.

== Commands

Inventory files and physical bytes:

[source,bash]
----
find /home/darwin/storage/lighthouse -type f -name '*.parquet' -printf '%h %s\n'
du -sh /home/darwin/storage/lighthouse
----

Read exact file and row counts from Parquet footers:

[source,sql]
----
SELECT
  regexp_extract(file_name, '/(2026-[0-9]{2}-[0-9]{2})/', 1) AS day,
  count(*) AS file_count,
  sum(num_rows) AS row_count,
  sum(file_size_bytes) AS byte_count
FROM parquet_file_metadata('/home/darwin/storage/lighthouse/*/*.parquet')
GROUP BY day
ORDER BY day;
----

Verify event-time coverage from row-group statistics:

[source,sql]
----
SELECT
  regexp_extract(file_name, '/(2026-[0-9]{2}-[0-9]{2})/', 1) AS directory_day,
  min(try_cast(stats_min_value AS TIMESTAMPTZ)) AS min_timestamp,
  max(try_cast(stats_max_value AS TIMESTAMPTZ)) AS max_timestamp,
  count(DISTINCT file_name) AS file_count
FROM parquet_metadata('/home/darwin/storage/lighthouse/*/*.parquet')
WHERE path_in_schema = 'timestamp'
GROUP BY directory_day
ORDER BY directory_day;
----

The representative profile queried row counts, timestamp bounds, distinct
resource/log/severity values, trace-field population, string lengths, JSON key
counts, and a reconstructed JSON object containing all Parquet columns.

The representative file was dominated by `generic_task` resources and the
OpenTelemetry collector-export log. Approximate selected cardinalities were 28
services, 427 pod UIDs, 328 task IDs, 25 shard values, and 16 `type` values.

Parsing and expanding every `raw_entry` as JSON did not complete within three
minutes for this single file and was stopped. This is not a ClickHouse benchmark,
but it supports parsing and normalizing source content once at ingestion rather
than repeatedly parsing raw text in interactive queries.

== GCP Volume Calibration

The workload reportedly accounts for approximately 32 TB/month in GCP Logging.
Projecting the observed 12-day row rate to 30 days yields approximately 16.7B
events/month and a provisional GCP-equivalent size of 1.9 KB/event:

This calibration must be verified against the exact GCP metric, log bucket
scope, exclusions, and calendar period. The reconstructed 5.46 KB JSON object is
not equivalent to GCP's pre-index entry measurement because reconstruction adds
field names and escapes the embedded raw entry.

== Interpretation

- The corpus provides natural contiguous subsets for provisional 1 TB and 10 TB
  tests.
- A provisional 100 TB test requires roughly eight time-shifted corpus passes.
- Event width and dynamic field count are large enough to expose attribute
  representation and storage-amplification problems.
- This corpus cannot validate trace-waterfall behavior or native metrics. Those
  require separate deterministic fixtures.
- Parquet compression cannot predict ClickHouse storage after indexes,
  projections, and materialized views are added.
