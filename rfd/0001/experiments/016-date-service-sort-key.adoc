== Question

What are the measured storage and query characteristics of placing
`toDate(timestamp)` and `service_name` before the full timestamp, rather than
inferring them from the fact that the table already uses daily partitions?

== Candidates

Date after the required tenant and dataset prefix:

[source,sql]
----
PARTITION BY toDate(timestamp)
ORDER BY (
    tenant_id,
    dataset,
    toDate(timestamp),
    service_name,
    timestamp,
    event_id
)
----

Date as the first sorting expression:

[source,sql]
----
PARTITION BY toDate(timestamp)
ORDER BY (
    toDate(timestamp),
    tenant_id,
    dataset,
    service_name,
    timestamp,
    event_id
)
----

Within a daily part, the date expression is constant, so both are expected to
have the same row ordering and service-first behavior. The date-leading variant
would not be acceptable if partitions could mix dates because it would place
time before the tenant-isolation prefix. Those expectations are hypotheses
being tested, not results.

== Method

. Use the same 2026-08-05 source day as Experiment 013: 548,954,103 rows and
   approximately 1.04 TB of provisional logical input.
. Load each candidate through 24 hourly windows, validating row count and event
   checksum after every insert.
. Compact to one active part before measurement so part layout does not
   confound the comparison.
. Run the same latest-tail, time-range count, service/severity, and dynamic
   `Map` filter fixtures over 5-minute, 1-hour, 6-hour, and 24-hour ranges.
. Run three ClickHouse-cold and three warm repetitions and capture wall time,
   rows, bytes, marks, CPU, and memory.
. Require every result hash to match the timestamp-first results from
   Experiment 013.
. Preserve `EXPLAIN indexes = 1` for the representative full-day queries.

ClickHouse-cold resets ClickHouse-managed caches but not Linux page cache or ZFS
ARC. The run remains a single-host storage-layout test, not a distributed
capacity result.

== Guardrails

- Preserve the source, ten-day tables, Experiment 013 candidates, and immutable
  run artifacts.
- Preserve at least 100 GiB free on the benchmark SSD.
- Stop on a checksum mismatch, reference-result mismatch, partial window, or
  final part-count mismatch.

== Results

The controlled run completed all 48 checksum-validated load windows, all 192
timed queries, and eight representative full-day `EXPLAIN indexes = 1` plans.
Every result hash matched the corresponding timestamp-first result from
Experiment 013. Raw artifacts remain at
`/mnt/fast-storage/lighthouse/runs/experiment-016-date-service-v1`.

The run used ClickHouse 26.3.17.110, 12 query threads, a 40 GiB query memory
limit, and one final active part per candidate. ClickHouse-cold reset
ClickHouse-managed caches but not Linux page cache or ZFS ARC. Latencies below
are medians of three wall-clock measurements.

The compressed sizes differed by only 18,722 bytes across 111.61 GB per
candidate, or less than 0.00002%. Both builds loaded the same rows in nearly the
same time. This directly confirms that moving a date value that is constant
inside the daily partition did not produce a meaningful storage or load-layout
difference.

The candidates had nearly identical selected marks, rows, and bytes for every
fixture despite some wall-time variation. For example, the 24-hour service
query read 142,546,085 rows, 4.702 GiB, and 23,251 marks with date after
tenant/dataset, versus 142,543,655 rows, 4.702 GiB, and 23,259 marks with date
first. The observed latency difference therefore does not have an index-pruning
explanation in this evidence and must not be attributed to date position.

=== Index evidence

For full-day recent-tail, range-count, and dynamic-filter queries, EXPLAIN
reported:

* 90,543 of 90,543 primary-key granules for date after tenant/dataset;
* 90,735 of 90,735 for date first; and
* one range in both candidates.

For the service/severity query, the primary key retained 23,251 of 90,543
granules (25.68%) and 23,259 of 90,735 granules (25.63%), respectively. Both
plans used generic exclusion search with the same effective keys:
`tenant_id`, `dataset`, `service_name`, and `timestamp`. ClickHouse omitted the
constant date expression from the reported effective keys in both plans.

These plans directly support equivalent full-day index behavior. They do not
describe 5-minute, 1-hour, or 6-hour pruning; Experiment 017 will capture those
range-specific plans rather than extrapolating from the full-day plan.

=== Operational observations

Both initial `OPTIMIZE FINAL` attempts waited for existing background merges
and returned after the 120-second wait limit without reaching one part. The
harness rejected each multi-part result, retained all validated windows, and
resumed after background merges stopped. The successful final compactions took
35.4 and 35.6 minutes. Every timed query ran only after both candidates had one
active part.

== Interpretation

* Leading the sorting key with `toDate(timestamp)` has no demonstrated benefit
  under daily partitioning. It produced effectively identical storage, build
  cost, scan work, and full-day index plans.
* The date-leading candidate weakens the visible tenant-first invariant without
  adding measured pruning. The tenant/dataset prefix should remain first.
* Service-first ordering itself remains the source of service pruning. The date
  expression is redundant and can be omitted from the sorting key without
  relying on a performance estimate.
* The comparison with timestamp-first and hour/service layouts remains a
  cross-run comparison until Experiment 017 captures and correlates their exact
  range-specific plans. This record does not assign unexplained cross-run
  latency differences to an index.
