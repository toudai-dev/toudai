- *Status:* Completed

- *Data mutation:* Removed abandoned DuckDB spill files created during corpus

== Question

Should local ClickHouse storage experiments run in a container or as a native
process, and which local filesystem is appropriate for source data, ClickHouse
parts, and temporary files?

== Environment

- CPU: AMD Ryzen 5 3600, 6 cores / 12 threads, one NUMA node
- Memory: 62 GiB RAM, 68 GiB swap
- Native ClickHouse: 26.3.15.4 LTS from the repository's Nix environment
- Docker: 29.6.2, `overlay2`, 12 CPUs and host memory available
- Docker root: `/var/lib/docker` on the OS filesystem
- ClickHouse system service: inactive

== Method

The host was inspected without running an I/O benchmark. Commands included:

[source,bash]
----
lsblk -e7 -o NAME,TYPE,SIZE,FSTYPE,FSVER,MOUNTPOINTS,MODEL,SERIAL
df -hT
df -ih
zpool list -v
zpool status
zfs list -o name,used,avail,refer,mountpoint,compression,compressratio,recordsize,atime,primarycache,secondarycache
zpool get ashift,autotrim,autoexpand,fragmentation,capacity,free storage fast-storage
docker info
docker system df
clickhouse local --version
----

No `fio` or ClickHouse load test was run, so this record describes capacity and
topology rather than measured throughput or latency.

The source corpus is the only significant child at approximately 1.3 TiB and is
available at both `/mnt/storage/lighthouse` and
`/home/darwin/storage/lighthouse` through the host's mount arrangement.

Writing ClickHouse parts to this same pool while reading the Parquet source
would mix source reads, part writes, and background merge I/O on the same HDDs.
That can be useful as an explicit constrained-storage experiment, but it is not
a clean baseline for comparing schemas.

== Recommendation

=== ClickHouse execution

Run storage and query-performance experiments with the Nix-pinned native
ClickHouse 26.3.15.4 server as an unprivileged, dedicated process using a
versioned benchmark configuration. This avoids:

- accidental writes through Docker `overlay2` or OS-backed named volumes;
- ambiguity about container filesystem and cgroup behavior;
- the current Compose version mismatch (`25.8` versus native `26.3.15.4`);
- requiring container image availability for the exact Nix-pinned build.

Containers remain appropriate for application integration and end-to-end tests.
If a container is later included in a performance comparison, it must use the
same ClickHouse version and a direct bind mount to the same benchmark dataset;
the named volume must not be used.

=== Data placement

Use separate paths by responsibility:

[options="header",cols="2*"]
|===

|Responsibility
|Recommended location

|Immutable Parquet source
|`/mnt/storage/lighthouse`

|Primary 1 TB schema bakeoff parts
|dedicated child dataset under `/mnt/fast-storage/lighthouse/`

|Logs and benchmark metadata
|small dedicated path under `/mnt/fast-storage/lighthouse/`

|Bounded transient files
|dedicated path under `/mnt/fast-storage/lighthouse/`, with an explicit size limit

|Capacity/cold-tier experiment
|dedicated child dataset under `/mnt/storage/lighthouse-bench/`

|Docker integration data
|bind-mounted benchmark path, never the named volume

|===

Keep at least 15-20% of `fast-storage` free. The initial ClickHouse physical
footprint is unknown, so the 1 TB logical bakeoff must stop before total pool use
exceeds approximately 700-750 GiB. Run candidates sequentially or remove a
candidate only after its measurements and decision artifacts have been
preserved.

Do not use the OS NVMe for persistent benchmark parts. Reserve it for the OS,
Nix store, Docker integration images, repository work, and strictly bounded
temporary data.

== Filesystem Controls to Decide Before Loading

Create dedicated ZFS child datasets rather than writing directly into either
pool root. Record all properties with each run. Before the first load, decide
and document:

- whether ZFS compression is disabled to measure ClickHouse's own physical
  compression without double compression;
- whether the benchmark should compare ZFS compression off against the intended
  production setting;
- whether `primarycache=all` or `metadata` represents the target deployment;
- whether `recordsize=128K` remains the baseline;
- an explicit quota or refquota preventing a failed run from filling the pool;
- ownership and permissions for the unprivileged ClickHouse process.

Changing these properties is setup work and was not performed during this
read-only topology inspection.

== Interpretation

- Native ClickHouse is the cleanest initial performance baseline on this host.
- `fast-storage` isolates ClickHouse writes from the HDD-backed source and is
  appropriate for the first schema bakeoff if the measured physical footprint
  remains below its safe capacity.
- `storage` has enough capacity for larger compressed corpora, but source and
  destination contention must either be eliminated or treated as an explicit
  test variable.
- The local machine can establish relative schema behavior and single-node
  limits. It cannot by itself establish a production 100 TB or 1 PB distributed
  architecture.

== Follow-ups

- Create versioned native ClickHouse benchmark configuration and lifecycle
  commands.
- Create quota-limited ZFS child datasets after explicit approval for host
  storage changes.
- Measure sequential and random I/O separately on each target before loading
  ClickHouse.
- Run a small load calibration to estimate physical bytes per logical TB before
  committing to the full 1 TB bakeoff.
- Record the final native-versus-container choice as an architecture decision
  after accepting or revising this recommendation.
