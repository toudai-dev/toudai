== Question

link:../decisions/0003-rust-otlp-ingest-service.adoc[Decision 0003] replaces the
Go `toudai-collector` with `toudai-ingest` and archives the collector once this
experiment shows parity (D5). It also changes what OTLP success means: a request
succeeds only after the canonical and serving inserts holding its accepted records
have committed (D2). This experiment asks:

. Sent the same Experiment 023 fixture, do the Go path (collector #5) and
  `toudai-ingest` store the same rows, apart from the identity each assigns and the
  differences `toudai-ingest` makes on purpose (`ingest/src/mapping.rs` lists them)?
. Under stored acknowledgement, what do producers see, and what is stored, in the
  failure cases Experiment 021 injected into the Go path: ClickHouse stopped, a
  permanently broken destination, a split write, ambiguous inserts from both
  directions, a stalled destination with a full admission budget, a killed process,
  a producer resend, and a request mixing valid and invalid records?

== Hypothesis

Written before the first run.

*Parity.* For each transport, every fixture record stored by one path is stored by
the other, joined on dataset, signal, and `fixture.key`. Serving columns are equal
except `event_id` and `payload_sha256`, and `kind` on the application-event rows
(Go `log`, ingest `event`). Canonical payloads are equal once the schema name and
`identity.event_id` are set aside and the two documented payload differences are
applied (`span.events`, `kind`). Both paths reject the same two repeated-key records
and drop the same two spoofed `toudai.dataset` record attributes.

*Stored acknowledgement*, against `toudai-ingest` with its defaults (5 s request
budget, 1 s flush):

  bash rfd/0001/experiments/025-ingest-parity-and-acknowledgement/run.sh
----

The script builds `toudai-ingest`, the fixture emitter, and the collector; starts
ClickHouse; and runs every phase in order. Each parity run writes its own
database; the failure phases share one and count their rows by label. Every check writes its expected and observed
values to `results/checks.tsv`; expected values come from the hypothesis and the
injection, never from the observed rows. It exits nonzero if any check fails.

* *Parity.* For each transport, the emitter sends the fixture to the collector and
  then to `toudai-ingest`, each writing its own database. `compare.py` joins the
  stored rows on dataset, signal, and `fixture.key`, and allows a difference only
  in the exact form `ingest/src/mapping.rs` documents. `event_id` and
  `payload_sha256` are not compared. The Go path stores no span events, so only
  the shape of ingest's `span.events` is checked here; `ingest/tests/fixture_e2e.rs`
  checks their content against the fixture. The row dumps are kept in
  `results/parity/dump/`.
* *Failure phases.* `toudai-ingest` reaches ClickHouse through `relay.py`, an HTTP
  relay that can let an INSERT commit and then reset the connection or withhold the
  response. ClickHouse is stopped with SIGTERM, the canonical `payload` column is
  renamed, and `serving_logs` is renamed away. The stall phase points
  `toudai-ingest` at Experiment 021's stalled listener, which accepts connections
  and never answers. Each request carries one record with a unique label, and rows
  are counted by that label as canonical/serving.
* *Process stops.* A loader sends one single-record request every 40 ms; SIGKILL
  lands 1.5 s into a run of 60 requests, SIGTERM 0.4 s into a run of 20; requests sent after the signal find the port closed.

== Interpretation

*Parity holds for the fixture.* Over both transports, `toudai-ingest` stores the
rows the Go path stores, with the same rejections and drops, and differs only where
`ingest/src/mapping.rs` says it does. That is the parity condition of
link:../decisions/0003-rust-otlp-ingest-service.adoc[Decision 0003] D5 for the
Experiment 023 fixture. Archiving the collector is the next plan step and waits on
collector #5 merging.

*A 200 now means stored.* No acknowledged request was lost to SIGKILL, and none
was unreadable at its 200. What the producer sees is now honest in each case
where the Go path returned 200 regardless: an unreachable ClickHouse or a missing
table is a retryable 503, a write the client refuses outright (here the row check
against a renamed column) a non-retryable 500, a full budget an immediate 429, and
a rejected record appears in `partial_success`. The price is latency: at low
traffic a request waits for the 1 s flush, about 1.0–1.1 s. Experiment 021 saw
one Go row about 0.3 s after an immediate 200, an observation rather than a
latency measurement. The 10k events/s run measures latency under load.

*Duplicates remain, in smaller shapes.* Retrying only the failed destination
removes Experiment 021's 2/2 shape after a lost serving response; a lost response
now duplicates only the destination that lost it (2/1 or 1/2, one `event_id`).
When a failure outlasts the budget, the producer's resend adds a second identity,
so a split write leaves one orphan canonical row and a withheld serving response
leaves 2/2 under two identities. These are the at-least-once costs Decision 0001
D5 accepts; nothing deduplicates them.

*Unpredicted: an INSERT whose response never comes keeps its connection.* After
the relay withheld ClickHouse's answer to a fully sent INSERT, `toudai-ingest`
answered 503 at the deadline but left the connection open: the relay saw both
withheld connections close at 08:40:47.594, about 5.9 s after the canonical
one's 503 and 28 ms before the stall listener's start time, which is when
`toudai-ingest` had just been stopped (`results/phases/relay.log`,
`stall-listener.log`). The stalled destination did not show this: there
`toudai-ingest` closed every held connection at the 5 s deadline (two more
connections opened and closed within 2 ms at that deadline; this run does not
show what they carried). The cause is in
the `clickhouse` crate (0.15.3): it awaits an INSERT's response in a spawned task
and, when the insert is dropped, aborts only the request body, so once the body
is sent the task keeps the connection until the server answers. The stall phase
probably timed out earlier, in the crate's schema query, which is not spawned;
this run does not show which request was pending there. A ClickHouse that
accepts INSERTs and stops answering would hold one connection per timed-out
insert.

What the results do not cover:

* One run on one orb, with the debug build. Node loss, ClickHouse replicas, and
  the 10k events/s load are not exercised.
* The failure phases use OTLP/HTTP with JSON and logs only. gRPC status mapping
  and spans are covered by the crate's tests, not by this ClickHouse run.
* No SDK retry: resends are `curl` repeats of the same bytes.
* A kill between the canonical and serving commits of one flush was not targeted.
  It would leave canonical rows without serving rows for unanswered requests; none
  appeared in this run.
* Durable overflow does not exist yet, so ClickHouse unavailability is pushed back
  to producers rather than absorbed.
* Three Experiment 021 phases were not replayed: the identical-legitimate-events
  control (two byte-identical records in one request), `no-trust` (a request
  reaching the writer without its trusted scope, which `toudai-ingest` cannot
  produce because scope is a typed field set at admission), and the bounded
  serving-row repair, a SQL statement that does not depend on the write path.

== Follow-ups

* Bound the connection a timed-out INSERT leaves behind, for example with the
  crate's insert `end_timeout` (`Insert::with_timeouts`) set below the request
  deadline, which aborts the spawned task when it fires; test it with the
  relay's withhold mode.
* The 10k events/s hour against `toudai-ingest`, choosing between group commit and
  async inserts with wait (Decision 0003 D2).
* Real SDK retry behavior against stored acknowledgement (acceptance item "Verify
  what survives automatic retries of real OTLP SDK exporters").
* Collector deprecation and archive, with the RFD plan wording, once collector #5
  merges.
