== Question

Do the bounded tenant acceleration paths selected at one day preserve their
storage efficiency, build feasibility, correctness anchors, and interactive
latency over the completed 5,689,254,359-row, approximately 10.81 TB logical
corpus?

== Hypothesis

The generic two-field attribute index should grow roughly with field prevalence
and remain a small percentage of the 1,000.85 GiB normalized event table.
Five-minute count and duration aggregate states should remain much smaller than
the raw corpus and answer dashboard-shaped queries in interactive time.

The experiment does not assume linear build time or query latency. Part count,
merge work, cache behavior, and high-cardinality value distribution may change
at ten days.

== Candidates

Rebuild the same manually selected accelerations from Experiment 008 against
`benchmark.events_map_hot`:

. Generic string-attribute rows for configured `type` and `workspace_id`
   fields.
. Five-minute event counts by `service_name`.
. Five-minute duration count, sum, adaptive histogram, and t-digest states for
   the global distribution and configured `caller` dimension.

These are schema-stable shared tables keyed by tenant, dataset, field or
dimension name, and value. They do not create tenant-specific ClickHouse
columns and do not index every discovered field.

== Method

. Record the source table, row count, parts, storage, host state, ClickHouse
   settings, and repository revision.
. Drop only the three disposable acceleration tables from Experiment 008 and
   recreate them on the benchmark SSD policy.
. Build each selected path serially while recording elapsed time, rows and
   bytes written, CPU, memory, and part growth.
. Run raw and accelerated versions of two dynamic equality filters, rate by
   service, duration heatmap, and percentiles by caller.
. Run three repetitions under ClickHouse-cold and warm cache policies.
. Require byte equality for exact filter and rate outputs. For approximate
   aggregates, require identical sample counts and duration sums and report
   histogram or t-digest variation separately.

The selected fixture values match Experiment 011:

- `type = event_lifecycle`;
- `workspace_id = 7b10263c-4daa-44e4-9dde-d15c404b23e2`.

== Guardrails

- Preserve the raw hot-event and exact payload tables unchanged.
- Preserve at least 100 GiB free on the SSD dataset.
- Build and query serially; do not overlap external benchmark workloads.
- Stop on a partial build, correctness mismatch, unexpected source row count,
  or storage guardrail violation.
- Do not infer sustainable ingestion maintenance from asynchronous backfill.
- Keep activation manual; this experiment does not justify automatic tenant
  acceleration policy.

== Acceptance Criteria

- Every source query uses the ten-day `events_map_hot` table and records the
  expected 5,689,254,359 rows.
- All derived paths complete without changing source-table counts or checksums.
- Exact outputs match raw execution; approximate anchors match.
- Total derived storage and build resources are measured and remain within host
  guardrails.
- Accelerated medians and raw fallbacks are reported independently for both
  cache modes.

== Results

The controlled run `experiment-012-ten-day-acceleration-v1` completed all four
builds and 60 measured queries in 8 hours 8 minutes. The artifact is preserved
at `/mnt/fast-storage/lighthouse/runs/experiment-012-ten-day-acceleration-v1`.
It used ClickHouse 26.3.17.110 and repository revision `57be8c591d1e`.

The two selected index values are highly prevalent: `type = event_lifecycle`
matches 1,019,093,824 events and the selected `workspace_id` matches
296,875,155. The benchmark computes an exact checksum over every matching event
identity, so its 3.7-to-9.3-second accelerated latency is a demanding full-match
aggregate rather than bounded raw-event retrieval. It is a major improvement
but still not a two-second interactive path for these values. Selective values,
top-K counts, and bounded event retrieval require separate fixtures.

The aggregate states meet an interactive dashboard envelope on this host at
75-to-124 ms. Cache mode has no material effect because they read tiny derived
tables rather than the raw corpus.

=== Correctness

All 30 raw-versus-accelerated checks passed:

- exact filter counts and event-ID checksums matched;
- all rate buckets matched;
- heatmap sample count and duration sum matched; and
- every returned caller's percentile sample count and duration sum matched.

The stored heatmap and t-digest states returned stable bytes across measured
queries because their expensive merge order was fixed during the build. They
remain approximate and may differ after a rebuild or different ingestion merge
order. The product still needs fixed compatible heatmap buckets or another
explicit sketch contract, numeric tolerance for approximate percentiles, and
exact raw fallback.

== Interpretation

Bounded, schema-stable acceleration remains viable at ten days without
tenant-specific ClickHouse columns. Dashboard aggregate states are the strongest
result: they add about 42.5 MiB and turn 12-to-17-minute raw queries into roughly
0.1-second queries.

Configured attribute indexes also scale physically: two extremely prevalent
fields add 31.76 GiB, or 3.18% of normalized storage, and improve exact
full-match aggregates by 49× to 263×. However, 3.42B derived rows, approximately
1.5 hours of serial backfill, and multi-second queries for prevalent values
confirm that indexes must be budgeted per tenant and field. They should support
selective filters and bounded drill-down, not replace aggregate states or raw
storage.

This result supports manual and dashboard-requested activation with raw
fallback. It does not yet justify automatic activation because sustainable
ingestion maintenance, per-tenant skew, selective and absent values, expiration,
backfill isolation, and mixed concurrency remain unmeasured.

== Follow-ups

- Measure selective, absent, range, conjunction, and bounded event-retrieval
  index queries.
- Maintain the derived paths during representative ingestion and measure lag,
  merge load, and write amplification.
- Run asynchronous tenant backfill beside dashboard and exploratory workloads.
- Simulate multiple tenants selecting different fields and one noisy tenant.
- Replace the adaptive heatmap contract with fixed buckets or a measured
  mergeable sketch before defining dashboard API semantics.
