== Question

Which ClickHouse indexes and key conditions were actually available to every
measured SELECT workload, how many parts and granules did each stage retain or
discard, and how does that access plan correlate with measured rows, bytes,
CPU, memory, and latency?

== Evidence standard

This audit must not infer an index path from latency or selected-row counts.
Every conclusion requires a saved `EXPLAIN indexes = 1` plan produced against:

* the exact table DDL and ClickHouse version used by the measurement;
* the exact rendered query text and parameter values;
* the exact time range and relevant settings; and
* an equivalent part layout, with differences explicitly recorded.

Plans reconstructed after an experiment must be labeled *reconstructed*, not
presented as artifacts captured during the original timed run. If any required
input or physical layout cannot be reproduced, the record must say
*not reconstructable* and identify the missing evidence. A similar query or
schema is not an acceptable substitute.

Experiments 000–004, 006, 009, and 010 are data profiling, host/runtime,
ingestion, storage-layout, or load experiments rather than SELECT-performance
comparisons and do not require query-plan backfill. Experiments 014 and 015 are
planned and must include plan evidence when their query phases run.

== Method

. Wait for Experiment 016 to reach a terminal state so audit queries cannot
  perturb its load, compaction, or timed-query phases.
. Recover each historical run's fixture files from its recorded repository
  commit rather than assuming current fixtures are identical.
. Recover parameters, time bounds, ClickHouse version, and settings from the
  run manifest and query log.
. Verify table DDL, row count, parts, and marks against retained evidence before
  classifying a plan as exact reconstruction.
. Rebuild missing historical tables under isolated names only when all inputs
  and the physical layout can be reproduced. Record rebuild checksums.
. Save normalized query text, `EXPLAIN indexes = 1`, table DDL, part evidence,
  and a machine-readable index-efficiency summary for every plan.
. Join each plan to the original timing and query-log metrics by fixture,
  candidate or path, time range, and cache mode. Explain cache effects
  separately because EXPLAIN describes planning and pruning, not cache hits.

== Required correlation

For every measured fixture, report:

* partition, primary-key, projection, and skipping-index conditions;
* selected versus total parts and granules at each index stage;
* the resulting ranges and search algorithm where ClickHouse reports them;
* median measured rows, bytes, CPU, peak memory, and wall latency;
* whether latency changes track pruning, compression, cache state,
  aggregation work, sorting, or another directly measured factor; and
* unresolved effects where the evidence cannot isolate causality.

The write-up must distinguish correlation from causation. It must not claim an
index caused a latency change unless candidate controls or measured scan work
support that conclusion.
