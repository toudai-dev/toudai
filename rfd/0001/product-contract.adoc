= Product contract

This section defines the product boundary and common event contract.

== Product contract

The target workflow is:

....
alert -> compare time ranges -> group by any retained field
      -> identify an outlier -> inspect exact representative events
....

Lighthouse adopts Scuba's flexible event exploration, mandatory time bounds,
storage-node partial aggregation, and fast drill-down. It does not adopt
Scuba's memory-authoritative serving, silent sampling, short-only retention, or
unlabelled incomplete answers. Kraken is supporting evidence for future scale
techniques, not the product model or an immediate reason to build a custom data
plane.

The MVP supports filtering, grouping, time series, rates, histograms, heatmaps,
percentiles, top-K, comparisons, and bounded raw-event retrieval. Joins and
arbitrary general-purpose database workloads are outside the interactive path.
Every query requires an authorized workspace, dataset, and bounded time range.
Accounts own workspaces, and workspaces own datasets and ingestion keys; see
link:tenant-policy-and-isolation.adoc#_accounts_workspaces_and_keys[workspace isolation].
Existing "tenant" terminology denotes workspace scope, not the owning account.

Completed multi-day measurements characterize the benchmark fixtures; they do
not establish product SLOs. Prospective PoC latency and freshness targets are in
link:experiments-impl.adoc[the experiment plan]. Offered load, concurrency,
retention, and cost budgets must be fixed before acceptance runs.

== Event and instrumentation contract

Standard OTel producers emit OTLP. The Collector path maps logs, spans, and
application events into a versioned internal envelope containing authenticated
tenant/dataset scope, event identity, timestamps, kind, service/deployment context,
trace correlation, typed attributes, canonical payload, and available sampling
metadata. Proprietary batch IDs and receipts are not required of OTel clients.

Instrumentation libraries must be asynchronous, batched, compressed, and
backpressure-aware. They expose accepted, rejected, retried, sampled, and
dropped counts. They must not silently sample. Preserve supplied upstream sampling
metadata and provenance; missing probability/weight remains unknown. The PoC
reports observed-event aggregates without automatic population extrapolation; see
link:queries-and-acceleration.adoc#_upstream_sampling_and_observed_event_results[sampling semantics].

Ingestion validates field count, field-name growth, event and string sizes,
declared types, reserved fields, and sensitive-data policy before database or
overflow export. OTLP acknowledgements and partial failures follow the tested
Collector configuration, not a custom atomic-batch protocol. Additive fields are permitted; incompatible type changes are
recorded and rejected or isolated according to versioned tenant policy.

== Implementation language

Lighthouse uses Rust for the service and benchmark load generators. This was a
low-cost choice because the repository contained only a three-line Go
placeholder and no Go dependencies, generated code, or tests. Rust provides
the asynchronous I/O, explicit resource control, and Arrow/Parquet ecosystem
needed by the ingestion and replay paths without making a custom storage engine
part of the MVP. Reusing the OTel Collector does not require rewriting its
components in Rust; custom extensions need a demonstrated compatibility gap.
ClickHouse remains the serving engine. Revisit the language
only if implementation uncovers a concrete interoperability gap that is more
expensive than maintaining a second runtime.

== Alternatives

Separate log and span tables were rejected as the user-facing storage boundary
because cross-event exploration and trace-correlated logs are core behavior.
Separate physical components remain permissible behind the unified contract
when measured access paths require them.

Putting native metrics into the event table was rejected because it combines
incompatible semantics without improving event exploration. Keeping only raw
JSON was rejected because common routing and filtering repeatedly pay extraction
cost. Indexing every field was rejected because its amplification is unbounded.
Ingestion sampling was rejected because it conflicts with full-resolution
accepted data.

== Open decisions

The proposal cannot move to `committed` until the implementation checklist's
MVP exit criteria are met. The key unresolved choices are explicit SLOs and
retention, initial tenant budgets, synchronous versus asynchronous exact-query
limits, and whether archived events are queried through object-backed parts or
a separate archive path. Write identity, at-least-once delivery, payload
placement, and epoch-based placement are decided for the PoC in
link:decisions/0001-poc-physical-layout.adoc[Decision 0001]; deduplication and
the shard count at which dataset-aware shard groups replace whole-cluster fanout
remain qualification decisions.

== Context

Lighthouse is being designed as a ClickHouse-backed, Scuba-style telemetry
system for recent-data exploration. The initial proof of concept lives at
`~/workspace/inngest/lighthouse` and provides useful ingestion, query-planning,
Prometheus compatibility, schema, and staging performance evidence. This
repository is not required to preserve the proof of concept's physical schema.

The product workload, rather than Scuba's exact implementation, is the north
star: an engineer should be able to move from an alert to a time comparison,
group by any useful field, identify an outlier, and inspect representative exact
events without first predicting that query at ingestion time. The MVP contract
is intentionally not final until the agreed workload and prospective targets
are validated end to end; completed storage benchmarks alone do not satisfy it.

The product should provide a high-level event model rather than force users to
choose between logs and traces:

* logs, trace spans, and application-wide events share one event medium;
* a trace is a rendering of correlated events with span relationships;
* raw events remain available at full resolution without ingestion sampling;
* users can filter, group, aggregate, build heatmaps, and calculate percentiles
  over any retained event field;
* common dashboards remain fast through derived storage without limiting raw
  exploration;
* native metrics use separate time-series storage because their data model and
  access patterns differ from events.

The available performance corpus is under `~/storage/lighthouse`. It originated
as JSON log entries retrieved from GCP Logging and was compacted into Parquet.

== Goals

* Store logs, spans, and arbitrary structured events through one logical event
  medium with a common envelope. The query-serving columns and exact payload
  may use separate physical tables or tiers.
* Retain every accepted event and its queryable context at full resolution.
* Support exact raw queries and approximate or exact aggregate execution.
* Make interactive, arbitrary exploration possible without predeclaring every
  future query dimension.
* Accelerate known dashboard and incident workflows with bounded attribute
  indexes, materialized aggregate states, metadata catalogs, caching, and query
  routing while preserving raw fallback.
* Preserve field-type information in the logical contract and canonical event;
  use the benchmark-selected `Map` serving representation plus typed promoted
  columns or aggregate inputs only when measurement justifies them.
* Validate behavior at 1 TB, 10 TB, and 100 TB of GCP-equivalent uncompressed
  event data before considering a 1 PB clustered test.
* Measure storage amplification across the complete schema, not only base-table
  compression.

== Non-goals

* LogSQL or LogQL compatibility is not required in the initial design.
* A 1 PB benchmark is deferred until the 100 TB architecture is understood.
* Native metrics do not need to share the physical event table.
* Every arbitrary query is not required to have dashboard-class latency.
* Rollups do not replace or expire the full-resolution source events.
* Fully automatic physical-schema mutation is not an MVP requirement.
  Dashboards may request accelerations explicitly, and workload observation may
  recommend them; automatic activation requires per-tenant storage, field,
  cardinality, and backfill-CPU budgets.

== Settled Design Principles

== Unified events

One logical `events` medium stores logs, spans, and application events. Its
normalized query-serving table and exact canonical payload may be physically
separate. An `event_kind` discriminator affects ingestion validation and
rendering, not the event's queryability. Common queries can aggregate all event
kinds together.

Trace-specific fields such as trace ID, span ID, parent span ID, span kind, and
duration are nullable or have empty defaults for non-span events. Logs carrying
trace context are returned with spans when querying a trace.

== Separate native metrics

Native Prometheus or OpenTelemetry metrics remain in signal-specific tables.
Prometheus API compatibility remains useful for native metrics and dashboards,
but it must not define the event query model.

Event-derived counts, rates, histograms, heatmaps, and percentiles are computed
from raw events or event aggregate states. They do not require conversion into
native metric samples unless a later interoperability feature needs it.

== Full-resolution acceptance and retention

Lighthouse does not silently sample accepted events. Preserve canonical events
at full resolution within declared retention. The Collector PoC must distinguish
OTLP receipt/queue admission from confirmed storage and establish the supported
failure envelope. Recovery uses retained canonical data and tested backups;
overflow is not a complete archive. Independent all-event archival remains open. Producer
drops or upstream sampling must be reported where known; retain supplied sampling
probabilities/weights without inventing them when absent. Approximate percentile, distinct-count, top-K,
or histogram functions may be used for interactive execution, but this changes
the aggregation algorithm rather than the retained data. Exact execution
remains available with cost guardrails or as an asynchronous job.

== Raw fallback

Attribute indexes, materialized aggregate states, and projections accelerate
supported query shapes. A query using an unmaterialized field falls back to raw
events rather than becoming invalid. Query responses must disclose whether an
aggregate is exact or approximate.

== Standard distributed data plane

Scale beyond one node with local `ReplicatedMergeTree` tables behind a
`Distributed` table. Initially shard by a stable hash of `tenant_id`, `dataset`,
and `event_id` so high-volume tenants use the whole cluster. Accept broad query
fanout until measurements show that its fixed cost or network use justifies a
virtual-partition placement layer. See
link:README.adoc[RFD 0001].

== Bounded derived storage

Do not expand every attribute of every event into inverted index rows. Derived
tables must have a measured query benefit and a bounded amplification model.
Field-name and field-value discovery must use metadata catalogs rather than
array-joining the raw corpus at request time.

== Draft MVP Event Contract

Instrumentation emits a versioned common envelope. Logs, spans, and application
events use the same acceptance and query path; `event_kind` controls validation
and rendering rather than selecting a separate store. The logical contract
contains at least:

[source,text]
----
identity       tenant_id, dataset, event_id; internal write identity if required
time           source timestamp, observed timestamp
kind           event, log, or span
common fields  event name, service, environment, region, host, build, severity
trace context  trace ID, span ID, parent span ID, span kind, duration
dimensions     sparse string, boolean, and integer fields
measures       sparse integer and floating-point fields
sampling       supplied probability/weight and provenance, or explicit unknown
payload        exact canonical source event or immutable payload reference
schema         envelope and field-policy versions
----

The OTel SDK and Collector mapping is part of the data model. Reuse standard SDK
batching and transport behavior; bound application blocking and report drops and
backpressure. Preserve source timestamps and supplied IDs, and specify internal
identity assignment where OTLP provides none. Avoid sending known secrets or
unrestricted request bodies. Define a standard OTLP application-event encoding
before considering a separate wide-event API.

The MVP ClickHouse serving table uses fixed columns for the routing and commonly
queried envelope plus `Map`-based long-tail attributes. Canonical payload must be
retained for exact retrieval and reconstruction, potentially in a separately
ordered bulk ClickHouse table. Backup/restore and optional independent archival
are evaluated in the acceptance plan. This is a physical implementation
of one logical event medium, not separate log and trace products.

The PoC physical layout is fixed in
link:decisions/0001-poc-physical-layout.adoc[Decision 0001]: the sort key
`(tenant_id, dataset, timestamp, event_id)` from Experiments 013, 016, and 017,
daily partitions, the Experiment 021 typed Map layout with resource, scope, and
record namespaces, canonical payload on an S3-backed disk, a routing-epoch stamp,
and gateway-assigned write identity. Those experiments do not settle
mixed-workload production DDL, so the ten-day load of that layout and later
qualification must still determine:

* whether the timestamp-first baseline remains appropriate under sustained
  ingestion, merges, and the agreed service-filtered and tail-query workload;
* whether fixed-width identifier encodings pay for themselves over the measured
  `String` columns;
* which GCP and OpenTelemetry fields deserve fixed or materialized columns;
* retention behavior, hot-cache window, and archive format for the object-backed
  payload; and
* whether payload lookup latency from object storage stays within the bounded
  lookup target across the retention window.

Multi-tenancy does not imply one promoted column per tenant field. Fixed or
materialized columns are reserved for common envelope fields or fields with
exceptionally broad, measured benefit. Tenant-specific equality acceleration
uses the schema-stable `(tenant_id, dataset, field_name, field_value, timestamp,
event_id)` shape validated in Experiment 008; tenant-specific dashboard
rollups likewise store configured dimensions as data. This allows different
tenants to accelerate different fields without divergent ClickHouse DDL.

== PoC typed-value contract

Preserve the received OTLP value type; do not infer a type from string content.
The reference is the
https://opentelemetry.io/docs/specs/otel/common/[OpenTelemetry AnyValue model].
Pin the protocol/Collector versions used by compatibility tests. Canonical data
preserves strings, booleans, signed 64-bit integers, double-precision floats,
bytes, arrays, maps, and explicit empty values within configured size/depth
limits. This is semantic preservation after declared policy transformations,
not preservation of original protobuf wire bytes or data already dropped by an SDK.

For the initial query surface, support scalar strings, booleans, integers, and
finite floats, plus explicit presence/type predicates. Preserve bytes, arrays,
maps, and non-finite floats for canonical retrieval, but reject unsupported query
operations on them with an explicit error. Nested traversal and collection
aggregation are later extensions, not reasons to stringify or discard content.

Field identity includes its namespace: resource attributes, instrumentation-scope
attributes, record attributes, body, and reserved envelope fields do not overwrite
one another. Preserve case and literal attribute keys; a dot in a key does not
implicitly define nesting. Reject duplicate keys within the same incoming
attribute collection rather than depending on an exporter-specific winner.

Missing, explicit empty/null, empty string, false, and numeric zero are distinct.
Presence tests use key membership, never the default value of a missing Map key.
Scalar comparisons require matching types; the query planner does not silently
coerce strings, integers, or floats. Type changes across events are recorded as
multiple observed types, not converted to the first observed type. Group keys
include type, so string `"1"`, integer `1`, and float `1.0` remain distinct.

Numeric aggregations declare their input type; an incompatible non-empty value
is an error unless an explicit type filter excludes it. Missing/empty inputs do
not become zero; report contributing-value counts separately from event counts.
Integer values must not pass through floating point during storage or transport:
test integers above 2^53. Define overflow and result encoding before exposing
integer aggregates; reject overflow rather than wrap. JSON responses must encode
large integers losslessly with explicit type information, not rely on client
number precision. Casts and mixed integer/float aggregation are deferred.

Keep timestamp and duration units explicit and preserve received nanosecond
precision where present. A missing duration is not a zero-duration span; malformed
span timing must be rejected or explicitly flagged, never converted by unsigned
underflow into a huge duration. The accepted policy for a span whose start or end
is unset or whose end precedes its start is to preserve the span and its supplied
timestamps, keep the derived duration unavailable rather than zero, and carry an
explicit machine-readable timing diagnostic (Experiment 021). OTLP has no
timestamp presence — an unset timestamp is 0 — so missing timing takes precedence
over the reversed classification: a missing start never fabricates a duration from
epoch 0 and a missing end is never read as reversed. Missing timing, reversed
timing, and a valid zero duration stay distinct, and how an unavailable duration
is presented to a user is a rendering decision rather than a reason to discard or
fabricate the span. Metric values retain their separate OTel signal semantics;
this scalar event contract does not redefine native metrics.

== Open Questions

* What exact GCP metric and bucket scope produced the 32 TB monthly figure?
* What retention targets apply to local, object-backed, and archival data?
* What are the interactive p50/p95 latency targets by query class and time
  range?
* What dashboard and exploratory concurrency must one deployment support?
* What producer-to-query and overflow catch-up lag defines healthy ingestion?
* Which acknowledgement, retry, and duplicate guarantees can the
  link:acceptance-and-replay.adoc[Collector-first pipeline] support, including
  rebatching, ambiguous writes, and object-notification redelivery?
* Is exact aggregation required synchronously above a bounded scan cost, or may
  it run as an asynchronous query job?
* Which common envelope fields justify physical columns across tenants, and
  what evidence threshold permits adding one?
* What initial per-tenant event-size, field-count, field-name-growth,
  cardinality, scan, group, and derived-storage budgets are safe?
* At what shard count or workload mix does broad `Distributed` fanout justify
  targeted virtual partitions?
* Which fields must be searchable as text versus exact structured values?
* How long must exact canonical payload remain online, and when may it move from
  recent bulk lookup to archival retrieval?
* Do canonical retention and tested ClickHouse backups meet recovery objectives,
  or must every event also enter an independent archive?
* Should archived canonical events be queried through ClickHouse object-backed
  parts or through a separate archive execution path?
* Which registry technology should own dataset, field, privacy, quota, and
  acceleration policy, and what degraded behavior is allowed when it is
  unavailable?
